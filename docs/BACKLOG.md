#### 切り分けの道具（`match.html`。**消さないこと**）

    ?flat=1    牌の厚み（::before）を消す
    ?flat=2    ＋ 牌そのものの3Dをやめる
    ?flat=3    ＋ 卓の傾きと遠近をやめる
    ?nofit=1   **役目を終えた。**見張りは消えたので、この旗はもう何も飲まない
               （付けても付けなくても同じ結果になる。それ自体が錠になっている）
    ?bb=1      ブラックボックス。対局のあいだ毎秒一行を控えて、読み直したときに見せる
    ?fourjs=0  `.four` は付けたまま、JS 側の分岐だけを消す（`?nofit=1` を含む）

**原因は分かったが、道具は消さない。**`?bb=1` は次に実機で何かを追うときに
そのまま使えるし、`?nofit=1` の包みは**見張りが戻ったことを検出する錠**として
働いている（`check-bb.js` [5]）。消すときはその理由をここに書くこと。

`?nofit=1` は `match.js` の `setInterval(…, 500)` を止めるもの。`Match` は
`fitFour` を外に出していないので、`src/` を読む前に `window.setInterval` を
差し替えて**間隔 500 の登録だけ握り潰す**。**寸法は初回の一回だけで固定され、
以後は追随しない**（画面の向きを変えても直らない）。`?flat=` と一緒に使える。

**二戦目でも効く**（2026年9月10日・段2.5 で直した）。それまでは
**「一本飲んだら元に戻す」**形で、**一戦目しか効いていなかった**
——`Match.play` は**対局ごとに**見張りを登録し直すので、二戦目から復活する
（実機の3本目で `?bb=1` の `sp` が 0 → 144 に戻って見つかった）。
いまは旗が立っているあいだ `ms === 500` を全部飲む。
**同じ形の包みを足すときは必ず「二戦目」を考えること**——
効かない道具より、**一戦目だけ効く道具のほうが悪い**（表が嘘になる）。
経緯と錠は `crash-spec.md` §4.1。

`?bb=1` は**ブラックボックス**（`docs/design/match/crash-spec.md` §3）。
対局のあいだ**毎秒一行**を `localStorage['jandol.bb']` の**60行の輪**に控える
——DOM の数・`<img>` の数・keyed の Map・`getBoundingClientRect` と
`--side` 系の `setProperty` の回数・イベントの回数・**1秒のタイマーの遅れ（`lag`）**・
**何の最中か（`w`）**。右下の印にも同じ一行が出るので、実機でその場で読める。
**読み直したとき、閉じていない走行があれば直近5行を画面に出す**
（この表示だけは旗が無くても出る）。読みかたは §3.5。
**メモリで殺されたのか、主スレッドが止まって殺されたのか**を、まずここで分ける。

`?fourjs=0` は**JS か CSS かの切り分け**（§4）。`.four` のクラスは付けたまま、
500ms の見張り（`?nofit=1` を含む）・`onOrientationChange` の登録・
`UI.localDelta` の三つを落とす。**落ちれば CSS、落ちなければ JS。**
`?nofit=1` と同じで**寸法は初回で固定**され、FLIP の向きも狂う（絵は崩れてよい）。
`onOrientationChange` は**関数の名前で弾いている**ので、`match.js` 側で
名前が変わったら効かなくなる——**印が出ているのに `?bb=1` の `sp` が0でなければ
効いていない**、で気づける。

右下に `flat=N` / `nofit` / `fourjs=0` / `bb` の印が出る。**印が無ければ効いていない**
——実機では開発者ツールが使えないので、「効かなかった」と「効いたけど落ちた」を
これで分ける。絵は崩れてよい。**打てて落ちないかだけを見る。**

**`src/match.css` には書かないこと。**GitHub Pages が `src/*.css` を10分キャッシュするので、
実機で古いものを見たまま「効かない」と誤読する。**`match.html` はURLにクエリが付くので
必ず新しく取れる**——だからインラインの `<style>` と `<script>` だけで完結させてある。

### `finish()` が `comp` を持たない契約済みの子で落ちる（気になる脆さ）

`taikai.js` の `finish()` の育成で `before.toFixed(1)` を呼ぶが、
`before` は `st.comp[id] ?? c.comp` で、**`JANDOLS` は `comp` を持たない**
（持っているのは `FREE_AGENTS` だけ。13〜21）。`st.comp` にその子の完成度が
入っていないと `undefined.toFixed()` で落ちる。

**本編の経路では起きない。**契約する口は二つ（`scout.js` の「契約する」と
`office.js` の遠征の交渉）で、どちらも `comp[c.id]` を `compFromRank` で埋めてから
`contracted` に足している。**踏むのはセーブの形が崩れたとき**——
`contracted` にいるのに `comp` が空、という組み合わせ。
`debug.html` のプリセットや、手で書いたセーブで起きる（段3 の検証で実際に踏んだ）。

**直すなら `finish()` ではなく入口を疑うこと。**あそこで `?? compFromRank(rank)` に

### `fitFour()` が 0.5秒ごとに卓を測り直している → **直った（2026年9月10日）**

`Match.play` が `setInterval(…, 500)` で `fitTable()` を回し続け、その中の
`fitFour()` が**二分探索で `--side` を入れては外接矩形を測る。**実測で
**`getBoundingClientRect()` を1回あたり166回・195〜275ms。**それが**0.5秒ごと**。

**ここには「これは再読み込みの原因ではなかった」と書いてあった。間違いだった。**
`?nofit=1` で止めても落ちた、というのが根拠だったが、**あの包みは一戦目にしか
効いていなかった**（`Match.play` は対局ごとに見張りを登録し直すのに、
包みは一本飲んだら元に戻していた）。段2.5 で直して測り直したら、
**見張りが動いている走行だけが落ちた。**上の「四人卓のときだけ…」が正。

**見張りは消した**（段A・`crash-spec.md` §8）。測るのは五つの機会だけで、
どれも `scheduleFit()` → `requestAnimationFrame` で一フレームに一回へ畳む。
性能の話としても片づいている——四人卓のあいだ半分の時間を測り直しに
使っていたのが、局の変わり目とリーチ札の付け外しだけになった

**残した決めごと**（消さないこと。次に `fitFour` を触る人へ）：

- **数値を決め打ちにしないこと。**36度倒したうえに透視が掛かっているので、

- **測る機会を数え上げたら、必ず錠を付けること。**ここには
  「向きが変わったとき・`visualViewport` が動いたとき・局が変わったとき、で足りるはず」と
  書いてあったが、**四人卓では足りなかった**——`fitFour` は左右の席プレートの位置で
  卓面の幅を縛るので、**リーチの札でプレートが広がったら測り直しが要る**（五つ目の機会）。
  段Bの突き合わせで見つかった。いまは `tools/test-match.js` が
  「プレートの幅を変えうる印」を数えていて、**足したのに数え漏らすとテストが言う**
- **席プレートは `offsetLeft` / `offsetWidth` で測ること**（`getBoundingClientRect` ではなく）。

### ローカルルール（卓ごとのルール差）

**先にやる小さいこと**（これだけ切り出して先行してよい。**2026年9月5日に入れた**）

`Game` のコンストラクタに `opts.rules` を受け取る口を開け、既定値 `RULES_DEFAULT` を
一つ置く。**`undefined` なら既定に落ちること。**分岐は一つも実装しなくてよい。

**設計方針**（実装時に詰める）

**個別のトグルにしないこと。**喰いタン・後付け・割れ目・赤の枚数・一発裏・ハコ下・

- 標準ルール — 喰いタンあり・赤あり。大半の大会

**検証すべき組み合わせが3〜4に収まり、臨場感はむしろ強くなる。**

### 大会の人数は4の冪しか通らない

`taikai.js` の `ladderOf()`（出走表の梯子）は 人数 → 4分の1 → … と割っていくので、
**4の冪を前提にしています。**`TOURNAMENTS` に `size: 32` の大会を足すと
`['32名','8卓','2卓','決勝卓']` と出て、**梯子が嘘になります。**

同じ前提が `runTournament` にもあります。`while (alive.length > 4)` を抜けた時点の
`alive` がそのまま決勝卓になるので、32人だと **決勝卓が2人**になり、
控えに書く `size: 4` とも食い違います。

**直すなら両方同時。**片方だけ直すと、画面と実際の卓がずれます。
着手条件は「4の冪でない `size` の大会を足したくなったとき」。
