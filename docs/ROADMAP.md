## 0. いま何が起きているか

直営雀荘が完成した（リニューアル5段階・配置3段階・月末決算）。
雀荘まわりに宿題は無い。

一方で、**ゲームの時間軸が二つに割れている。** 雀荘は日単位で動き、30日で月報が出て、
日当も毎日払っているのに、大会とスカウトは回数単位のまま。
雀荘だけがカレンダーを持っている。

ここから先に足したいもの（疲労・調子・遠征・アイドル活動・依頼）は、
どれも「日」が無いと置き場所が無い。**だから次の一手は雀荘の続きではなく、
日進行を一本にする事務所ハブ。**

## 1. コンセプト（これに全部を従わせる）

表紙の一文がそのまま定義。

> 全国の雀荘を歩いて雀ドルを見つけ、口説き、育てて、大会に出す。
> 最後は最強の八人「雀エイト」を、あなたの事務所で独占する。

各機能はこの**見つける・口説く・育てる・出す**のどれかに対応する。

| 機能 | 対応 |
|---|---|
| スカウト遠征 | 見つける |
| アイドル活動 | 口説く（`pop` を上げて条件を満たす） |
| 直営雀荘 | 育てる（資金・出番・`pop`） |
| 大会 | 出す（実力の証明） |
| 育成 | 育てる（`comp`） |

どれでもないものは入れない。

### 主軸：代表の身体は一つ

何が足りないゲームかを一つに決めた。**日数でも金でも人でもなく、代表の身体。**
代表は事務所（＝店）にいるか、遠征に出ているかの二択。
遠征に出れば店の代表戦を誰かに任せ、留守番組がアイドル活動をこなす。
配分の判断はここから生まれる。

### 終わりは無い。区切りはある

リリース後に依頼（イベント）を足していく運営型。だから

- 取り返しのつかない損失を置かない（疲労は回復しきる。離脱は必ず警告を挟む）
- セーブは前方互換（未知のキーを消さない。欠けたキーは既定値で埋める）
- 依頼は**条件で発火し、日付で発火しない**（後から足しても新規にも古参にも届く）
- 雀エイトは終わりではなく節目

## 2. 決めたこと（2026年9月3日の設計会議。変えるときはここを直す）

**時間**
- 全画面が `parlor.day` を読む。新しい日カウンタは作らない
- 一日は 朝（事務所）→ 昼（活動）→ 夜（事務所・日報）
- 配置は変更するまで継続。毎朝聞かない
- **店が無い日も日は進む。**開店は今のまま（50万を払うまで店は無い）。
  弱小事務所なので最初は店を持てない、が設計で、
  **「まず店を持つ」が序盤の最初の節目。**
  店が無い日は「営業しない日」として既存の締めをそのまま通す
  （卓0で `computeDay` → 客0・売上0・家賃0。日当だけが出ていく）。
  **日を進める場所を `settle` 以外に増やさない**

**地理**
- 新規開始時に事務所名と本拠地の県を選ぶ
- **見せる単位は47県、計算の単位は既存の6地方**。県→地方の対応表で繋ぐ。
  `aisho`・`area` は地方のまま
- 遠征の日数と費用は本拠地からの遠さ（`far` 0〜5）で決まる。
  日数は「移動」ではなく「その土地の雀荘をまわる日数」と考える
- 県の人口差は**ライバル事務所の密度**を主、遠征の粒度を従で表す。
  規模の小さい県は「弱い」ではなく「まだ誰にも見つかっていない」

**スカウト**
- 遠征は出発時に目的（探す／口説く）と同行者（0〜3人）を決める
- **口説くには現地で麻雀に勝つ。** 勝ったあと既存の `evaluate()` で条件判定
- 負けても永久失敗にしない。`favor` を貯めて帰り、次に来ればまた挑める

**留守番**
- 遠征中も店は毎日営業。代表戦は「留守を任せた子」が打つ（`simulateTable`）
- 任された子には出番が付き、`favor` が少し上がり、疲労が溜まる

**依頼**
- 大会・契約イベント・アイドル案件は**すべて「事務所に届く依頼」**。同じ表に載る
- 大会は自分から出るのではなく、事務所の格で招待が届く

**アイドル活動**
- `pop` の供給源。代表不要、1〜3人、`chara`（19種）で向き不向き
- **演出は作らない。** 日報一行とセリフだけ。成果は雀荘の「推しファン」として床に現れる
- 案件の一部は対局付き。送った子が打つ

**雀エイト**
- **強さと人気の二軸。** 大会とアイドル活動が両輪
- 全国上位八人の表として事務所の壁に出す。未契約の子もライバル事務所の子も載る

**疲労と調子**
- 疲労はプレイヤーが管理するもの（行動で溜まり休みで抜ける、`comp` の補間位置を一時的に戻す）
- 調子はプレイヤーが受け入れるもの（毎朝確定、疲労が高いほど悪い目が出やすい）
- 数値は再測してから置く

**キャラクター**
- 200人まで増やす。**絵は今のうちにまとめて作る**（`--sref` が効くうちに）。
  出すのは段階的でよい（データには全員いて、会える条件を開く）
- 更新の通貨はキャラではなく依頼。雀エイト（固定の頂点）を後から壊さない
- 県への割り当ては200人増員時にまとめて。人口比ではなく下限を置く

### なぜこの順か

- **[A] が最初なのは、他の全部が「日」を前提にするから。** 契約イベントを先に
  `RULES.event` に書くと、A4 の依頼テーブルと二重になる。事務所を先に作れば
  天城リオの解放も大会の招待もアイドル案件も同じ表の行になる
- **旧「次にやること」の1（契約イベント）は A4 に、3（推しファンの売上）は A5 に吸収された。**
  2（客タイプ効果）は独立しているので [A] の後に [B] として残る
- **A3 で公開判断ができる。** 遠征と留守番の骨格が遊べて、A4 で図鑑が埋まる
- **[C] を [A] に混ぜない。** 再測の範囲が広がりすぎる
- **[D] の絵だけは今すぐ始めてよい。** 設計に依存しない生産作業で、
  遅らせるほど画風が揃わなくなるリスクがある
- **[E] は見せ方の差し替え**で、A3 の県一覧が機能していれば急がない
- **[F] は A5 の雀エイト表で名前が出るところまでで止め、実体は後**

### 再測のタイミング

`docs/HANDOVER.md` §4 の調整済み数値を動かすのは **A3 の終わりと A5 の二回だけ。**
途中の段で個別に触らない。

- A3: スカウト一回の費用（3万→遠さ×人数＋日数）、遠征中の店の落ち込み、大会の日数換算、
  **開店前の日当**（店が無い期間の序盤の収支。開店資金50万に何日かかるか）
- A5: 疲労・調子、推しファンの売上反映（`computeDay()` の入力に `favor` を足す）
