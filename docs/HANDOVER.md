## 1. これは何のゲームか

全国の雀荘で「雀ドル」を発掘してスカウトし、事務所を大きくしながら、
大会で賞金と名声を得ていくゲーム。最終目標は最強の八人「雀エイト」を
自事務所で独占すること。麻雀そのものは本格派（イカサマなし・牌操作なし）。

四つの柱：**収集・経営・育成・本格麻雀**。
ここでいう経営は雀荘ではなく**自分の事務所**の経営。

### ここまでの経緯

1. 普通の四人麻雀（`mahjong.html`）
2. イカサマ20種を足した『忍雀』（`ninjaku.html`）
3. 雀荘経営シミュレーション『雀荘物語』（`jansou.html`）
4. 雀ドル収集＋事務所経営に方向転換（仮題「雀ドルを探せ」）
5. **いまここ** → 題名を「雀ドル発掘放浪記」に変更、四つの柱が全部つながった

1〜3は別作品として完成済み。麻雀エンジンとCPU思考はそのまま流用している。

## 2. いまどこまでできているか

**発掘 → スカウト → 所属 → 大会 → 実対局 → 賞金 → 事務所強化 → 次を探す。
この一周が閉じている。** 遊べる状態。

| 画面 | 状態 |
| --- | --- |
| 表紙 | 顔を敷き詰めた表紙、続きから／最初から、事務所の様子 |
| プレイヤー設定 | 名前と顔（12人から選択）。プレイヤーも女性の雀士 |
| チーム編成 | 初期メンバー10人から3人。組み合わせで講評が変わる |
| 大会 | 5種、出走表、卓割り、勝ち上がり、賞金、育成、昇段 |
| **実対局** | 自分が座る卓は実際に打つ。他の卓は数値処理。立ち絵・セリフ・おまかせ付き |
| スカウト | 雀荘をまわって発掘、契約条件10種の判定、事務所の拡張 |
| **直営雀荘** | シフト（昼・夕・夜）、設備4種、イベント6種、日次の収支、夜は自分も打てる |
| 名鑑 | 未発見はシルエット、発見済みは顔、契約済みは金枠と契約印 |
| **事務所** | ハブ。朝→昼→夜→朝。事務所名と本拠地の県、所属一覧、配置とシフト、遠征、届く依頼 |

### まだ無いもの

- 疲労・調子・雀エイト表（第五段）
- 全国マップ、団体戦、スポンサー、人気投票

### (1) 契約イベント — 6人の解放

天城リオを含む6人の解放。図鑑を埋めるために必須。

**推奨：雀荘の好感度(`favor`)を条件に組み込む。**
「ゲスト来店」でその子をもてなすと好感度が+15（普通の接客で+4）貯まる
仕組みがすでに動いている。たとえば
「好感度80以上＋事務所ランク5＋雀エイト選抜戦優勝」のような
三段の条件にすれば、雀荘に通わせる理由と図鑑の解放が一本の線で繋がる。
判定は `scout.js` の `RULES.event` を書くだけ。好感度の値は
名鑑かスカウトの画面に出したほうがよい（いまはどこにも表示していない）。

暫定条件で逃げるなら「雀エイト選抜戦優勝＋事務所ランク5」あたり。

**済んだ（2026年9月3日・第四段）。**上の推奨どおり、三段の条件
（好感度＋事務所ランク＋大会実績）を **`offers.js` の依頼テーブル**に書き、
**`RULES.event` は「その依頼を受けたか」だけを見る**形にした。

**条件を二か所に書かないこと。**`RULES.event` にも条件を直書きすると、
片方を直したときに必ずずれる。判定の正は依頼テーブルのほう。

経路は「話が届く → 受ける → その子の地方へ遠征して口説く → 現地で勝つ → 契約」。
**依頼を受けただけでは契約にならない**——会いに行くところまでが要る。
天城リオ No.001 は 好感度80／事務所ランク5／雀エイト選抜戦優勝 で届く。

### 賞金の配分

優勝100% / 準優勝32% / 決勝卓12% / 準決勝3.5% / 一回戦0.8%。

**四人とも別々に出るので、一人ぶんの期待値を4倍した額が事務所の収入になる。**
最初は決勝卓22%・準決勝9%で組んだところ、D級チームでも新人戦で平均16万入り、

D→C:2 / C→B:3 / B→A:4 / A→S:6。

定員 4 / 6 / 8 / 11 / 14、拡張費 0 / 300万 / 900万 / 2500万 / 6000万。

#### 顔ぶれを必ず書き残すこと（前の表が再現できなくなった）

**客足は出勤者の `pop` の合計で決まる。**だから「6人」とだけ書いても
数字は再現できない。前の表は

| 局面 | 客 | 一日の利益 |
| --- | --- | --- |
| 序盤 | 25人 | +3.3万円 |
| 中盤 | **88人** | +10.6万円 |
| 終盤 | 221人 | +26.1万円 |

と書いてあったが、**中盤の88人だけがどうしても出せなかった。**
序盤と終盤（初期メンバー3人／`JANDOLS` の先頭から12人）は一致するので、
中盤に誰を並べたのかが残っていなかったということ。
`measure-jansou.js` は顔ぶれを毎回出力するので、以後この取り違えは起きない。

一日の利益が下がって見えるのは、**臨時収入を入れていない**ため
（イベント・チップ・ボトルは乱数で、局面の比較には効かない）。
場代だけで測るのは前の表と同じ。

狙いは三つ。**開店資金50万は約15日で回収**できること。
一日の利益が**スカウト一回（3万）と釣り合い、大会（新人戦平均10万）を
超えない**こと。設備を全部盛る費用（約2000万）が**S級への貯金
（スカウト300万＋事務所ランク5に6000万）の途中の使い道**になること。

夜に自分の卓を出すと貸せる卓が一つ減るので、序盤の利益は
+3.3万→+1.5万に下がる。祝儀（トップで+2万）でほぼ相殺される。

調整の余地として認識しているもの：評判が上がりやすい
（黒字+1と満卓+1が毎日入る）。気になったら満卓ボーナスの条件を
「二つ以上の時間帯で満卓」に絞るのが手っ取り早い。

### 店が無い日も日当は出ていく（2026年9月3日・未再測）

事務所ハブの第一段で、**店が無い日も `parlor.day` が進む**ようになった
（`docs/design/office/spec.md` §1.2）。開店資金50万を貯めているあいだも
所属の日当（`wageOf` × 所属の全員）が毎日引かれる。

**上の三局面の実測は動いていない**——`computeDay()` にも設備にも触っておらず、
店が無い日は卓0で客0・売上0・家賃0を返すだけだから。
動いたのは**その手前、開店するまでの序盤の収支**で、
そこはもともと測っていなかった区間。

- 初期メンバー3人なら日当は一日 **12,000円**（`BASE_WAGE` 4000 × 3。
  初期メンバーは `salary` が小さい）
- 収入は大会の賞金だけ（新人戦で平均10万）。**大会はまだ日を消費しない**ので、
  いまは「大会を回して貯める → 店を持つ」が序盤の形になる
- **所持金はマイナスになりうる。**`settle` は前から
  `money + profit` を素直に書いていて、下限を置いていない。
  店が無い日が続けば赤字が積み上がる

**下限は付けない（2026年9月3日に決めた）。**マイナスは許すし、
ゲームオーバーにもしない。これは**「給料の遅配」**として扱い、
定員のソフト化（`docs/ROADMAP.md` [C]）で**離脱の警告**に繋げる。
払えていない状態が続くと雀ドルが事務所を離れる、という形にする。
だから `settle` に `Math.max(0, ...)` を足さないこと——足すと、
遅配が起きていること自体が見えなくなる。

**数字はまだ触っていない。**開店資金50万に何日かかるかは、
`office/spec.md` §11 の**第三段の再測**でまとめて見る。

### 遠征まわりの実測（2026年9月3日・A3 の一度目。**まだ何も動かしていない**）

`node tools/measure-office.js` で測った。数字を動かす前の記録。
**この時点では調整していない。**動かすときはこの節を書き換えること。

- **遠征の費用は、日数ぶんの店の利益より安い。**京都→大阪（far 0）で
  2日・3万円に対し、序盤の店は同じ2日で 6.7万円を稼ぐ。
  遠いほど差は開き、那覇（far 5）で 7日・18万円に対し序盤 23.4万円。
  同行者を連れると費用だけが倍・三倍になるので、そこで釣り合いを取る形
- **遠征中の店の落ち込みは、思ったより小さい。**同行3人でも
  序盤 −0.7万円／日、中盤 −1.8万円／日。**終盤はほぼ0**で、
  客数も 221人 から動かない——`computeDay` が
  `Math.min(capacity, demand)` で頭打ちにしているため、
  卓8まで増やすと出勤者の `pop` が余っている
- **代表が夜の卓に着いていた場合の落ち込みのほうが大きい**（序盤 −1.8万円／日）。
  遠征中は `joinNight` が効かないので、出していたプレイヤーはそのぶんも失う
- **大会1回の賞金（新人戦10万）は、店の一日の利益の 3.0日／1.9日／0.4日ぶん。**
  第四段で大会が日を消費するようになると、この比が意味を持つ
- **開店資金50万は、大会5回ぶん。**大会が1日を消費するなら6日、
  2日なら14日、3日なら24日で開店に届く（初期3人の日当は 12,000円／日）

### 日当は契約基準（2026年9月3日に揃えた。実測は動いていない）

**出勤の有無に関係なく、所属の全員に毎日払う。**
以前は `dayWorkers`（シフトが一つでも入っている子）の合計だった。

揃えた理由は `office/spec.md` §7.2。「日当は既に毎日払われているので、
遠征中の人件費は何も足さずに自動でかかる。これが日数の本当のコスト」と
書いてあり、**それには日当が出勤ではなく契約に付いている必要がある。**
店が無い日（§1.2）はすでに所属の全員ぶんを払っていたので、
二つの規則が食い違っていた。

**上の三局面の実測は動いていない。**どの局面も全員が出勤しているので、
契約基準でも出勤基準でも日当の額が同じ。`tools/measure-jansou.js` を
種を固定して前後で回し、**出力が一文字も変わらない**ことを確かめた
（客 25 / 82 / 221、日当の差は三局面とも0円）。

変わるのは**プレイヤーが誰かを休ませたとき**だけで、
以前は日当が浮いていたのが、いまは払い続ける。
**休みは「疲労を抜くために金を払う」選択になった**（疲労は第五段）。

#### 中盤の 88人 が再現できていない

`tools/measure-jansou.js` で三局面を測り直したところ、
**序盤 25人と終盤 221人は一致したが、中盤は 82人**になった。
バグではなく、**この表が「6人」としか書いておらず、誰の `pop` を
足したのかが残っていない**ため。客足は出勤者の `pop` の合計で決まるので、
顔ぶれが違えば数字も違う。

`measure-jansou.js` は**測った顔ぶれ（名前と pop と合計）を毎回出力する。**
以後この表を更新するときは、その行も一緒に残すこと。
いまの再現に使っているのは `JANDOLS` の先頭から6人（合計pop 472）。

### 卓の配置とコンボは、客数と売上を動かさない（2026年9月）

模様替え（`docs/design/jansou/placement.md`）で卓を自分で置けるようにし、
隣り合わせで**コンボ**が付くようにした。**ここで `computeDay()` には
一切触れていない。**上の実測がそのまま生きているのはそのため。

コンボが動かすのは次の7つだけ：

**誰が座るか・どれだけ居るか・誰から立つか・チップ・ボトルの格・
常連の進み・指名。**

`computeDay()` が返す `guests` と `sales` は、コンボが有っても無くても
1円・1人も変わらない（テストで、同じ `day` からコンボ有り無しの
タイムラインを組んで帯ごとに突き合わせている）。

理由は `spec.md` §1 と §5.3 にある。売上は**再生が始まる前に確定**していて、
帯ごとに Σ`pay.amount` ＝ `sales` を厳密に満たすようタイムラインを組む。
ここに一円でも足したら、その厳密一致が崩れて検証できなくなる。

#### チップは `pay` ではなく `bonus`（ここを間違えると崩れる）

くつろぎ席（卓＋ソファ）のチップは **300円/人**。これは場代ではないので、
`pay` ではなく **`bonus`（祝儀・お忍びと同じ臨時収入の経路）**に流している。

- `build` が `bonus{label:'チップ'}` を退店と同時刻に置き、合計を
  `summary.tips` に持つ
- `prepareDay` が `plan.tips` として控え、**`settle` が臨時収入に足す**
- 再生層は1円も増減しない（スキップでも通常再生でも同じ値になる）

**チップを `pay` に混ぜると、帯の Σ`pay` ＝ `sales` がその場で壊れる。**
上部バーの「本日」も、場代と臨時収入を分けて数えているので、
混ぜると何が合っていないのか分からなくなる。

大きさの実測：終盤（卓8・内装5・既定の配置でくつろぎ席が2卓）で
**一日およそ2万円**。場代47万円の4%、一日の利益26万円の8%ほど。
内装4（ソファ）が付くまでは0円なので、序盤の収支には影響しない。
手応えのための額で、経済の柱にはしていない。

### 月末決算は「見せるだけ」にした（2026年9月）

30日で締めて月報を出す（`docs/design/jansou/monthly.md`）。
**経済には一切触れていない。**上の三局面の実測がそのまま生きている
（実装の前後で `computeDay()` を2000日回し、客 25 / 87 / 221 が一致することを確認した）。

**ひと月が30日なのは恣意ではない。** `wageOf()` は前から
`BASE_WAGE + salary/30` で、日当は「月給の三十分割」だった。
30日で締めれば30日ぶんの日当がちょうど月給一人分になり、
月報の人件費が年俸表と突き合わせられる。
**`MONTH_DAYS` と `wageOf` の割る数は対。片方だけ動かさないこと。**

月末に賞与を置きたくなるが、置いていない。入れると上の三局面を
測り直すことになる。`spec.md` §6.1 が推しファンの売上反映を
先送りしたのと同じ判断で、**まず見せるだけを入れて、月単位の数字が
どう出るかを見てから決める。**

**常連は新しく作っていない。** `parlor.regulars` が4段階で既に動いているので
（`spec.md` §7）、月報は `stageOf` で数えているだけ。

#### 月給を月末に一括で払うのは、やらない

月の概念ができると自然に見えるが、合計は同じ（`salary/30 × 30`）でも
**現金の流れかたが変わる。**月末に大きな支出が来る形にすると、
月初に設備を買ったプレイヤーが月末に破綻する。
上の実測は**すべて一日単位**で取ってあるので、測り直しにもなる。

### おまかせ（対局からの降り方）

`game.js` はどの判断も `p.isAI` を見て分岐している。だから
**自分の席を `isAI = true` にすれば、以降は全部CPUが打つ**。
`opts.spectate` と同じ仕組みを途中から効かせているだけ。

ただし罠がひとつ。切り替えた時点で入力待ちの Promise が
一つ宙に浮いている。これを解かないと対局が止まったまま戻らない。
`UI.giveUp()` は `g.aiTurnAction` / `g.aiCallAction` を借りて
その一手だけ解いている。**自前で「ツモ切り」にしてはいけない。**
鳴いた直後は `drawnId` が null で、打てない牌を選んでしまう。

もうひとつ。局の結果画面（`#next`）を押させたままだと早送りにならない。
`UI.auto` のときは自分で送るようにしてある。

### セリフは性格（chara）で分ける。専用のパラメータは足していない

73人ぶん個別に書くと手に負えない。`characters.js` の `chara`
（性格・19種）が最初から全員に付いていたので、これを口調の分類に使った。
**新しいパラメータは要らない。** 人を足すときも `chara` を
既存の19種から選べば、セリフは自動的に付く。

場面は8つ（start / riichi / tsumo / ron / deal / call / draw / idle）。
`game.js` の `io.event` に `{ seat, kind }` を添える形にした。
第三引数なので、添えない呼び出しは今までどおり動く。

**顔は動かさない。**四人ぶんを並べておき、喋った人の枠だけ大きくする。
`initTachie()` が対局のはじめに一度だけ、卓と同じ順
（下家→対面→上家→自分）で組む。
一人ずつ入れ替える形にすると、誰が喋ったのか追えなくなる（実機で確認）。

顔を動かさない結果、**「顔は次の人・セリフは前の人」の取り違えが
原理的に起きなくなった。**以前あったタイマーでの追従制御
（`_talkUntil` / `bigArt()` / `showTachie()`）は不要になり削除した。
いま手番の人には `turn` を付けて薄く印を出すだけにしている。

**吹き出しは時間ではなく捨て牌の数で引っ込める**（`ui.js` の
`BUBBLE_TURNS`、いまは4切り。放銃の一言だけ +3）。
時間で測ると、早送りと通常速度で残る長さが変わってしまう。
局が変わったときも畳む。

**名前をそのまま `innerHTML` に混ぜないこと。**プレイヤーの名前は
入力された文字がそのまま入る。`initTachie()` は要素を組み立てて
`textContent` で入れている。`render()` のようにテンプレートで組む場所は
`esc()` を通す（`ui.js` の先頭にある。他の画面が持っているものと同じ）。

### 立ち絵は #table の外・#app の中に置く

`#tachie` を `#table` の中に入れてはいけない。`#table` は
`overflow-y:auto` なので、絵が捨て牌と一緒にスクロールして流れていく。
置き場所は `#app` の中、`#table` と `#myarea` のあいだ。
縦持ちではそこが「自分の捨て牌の下」になる。
広い横画面のときだけ `position:fixed` で右の余白へ飛ばし、
`#app` に `margin-right` を付けて場所を空けている。

**縦持ちは顔を横に並べ、広い横画面は右の余白に縦へ積む。**
`.tcRow` の `flex-direction` をCSSで入れ替えているだけで、DOMは一つ。
`position:fixed` に変わるのも広い横画面のときだけ。

**縦持ちで余りをもらう仕掛け。** `#table` を `flex:0 1 auto`
（中身なりの高さ）にして、余った高さを `#tachie` が `flex:1 1 auto`
で全部もらう。序盤は顔が大きく出て、河が埋まるにつれて自然に縮む。
`min-height:96px` / `max-height:40dvh` で振れ幅を止めている
（縦の狭い画面では 84px / 32dvh）。
喋った枠は `flex-grow:2.6` で広がる。

**CSSの罠が三つある。**

1. 絵をグリッドの中に置いて `aspect-ratio` と `align-self:stretch` を
   併用すると、幅と高さがお互いを参照して決まらず `min-width` まで潰れる。
   **絵は `position:absolute` にして幅を割合で決めること。**
2. 縦持ちの `max-height:40dvh` は横持ちにも効いてしまう。
   横持ちの節で `max-height:none` に戻していないと、顔が潰れる。
3. `left` と `right` と `width` を同時に指定すると `right` が無視される。
   横持ちは `right` と `width` だけで置いている。**`left` を足さないこと。**

見た目を変えたら、必ず**縦横の両方**を描画して確かめること。
Puppeteer と Chrome をローカルに入れて、`python3 -m http.server` 越しに
開けば撮れる（`file://` だと画像が読めない）。

顔の画像は `initTachie()` が対局のはじめに一度だけ入れる。
以後は差し替えないので、読み直しによる点滅も起きない。
**組み直しの合図（`_tachieReady`）は対局ごとに戻すこと**
（§5「UIは対局をまたいで使い回される」）。

### 卓は「列レイアウト」であって四方の卓ではない

四人が四方に座る形（回転した牌）は**一度やめた**。
回転した牌は読みにくく、左右の河が縦に伸びて卓の高さを食い、
自分の捨て牌が画面外に押し出されていた。いまは各家を
「手牌の行」「捨て牌の行」の二行ずつ、上から順に積んでいる。

`ui.js` の書き出し先（`#top` / `#left` / `#right` / `#river-*`）は
そのままで、`#center` に `display:contents` を当てて
`#table` 直下に並べ替えている。**戻したくなったときは
`match.css` の「列レイアウト」の節を外せば、`style.css` の
四方のグリッドがそのまま復活する。**

雀魂のような見た目にしたい場合、この判断を覆すことになる。
横向きのときだけ四方に戻す、という折衷は可能。

4人麻雀で端数なく勝ち上がれるのは 4 / 16 / 64 だけ。

- **16人** → 4卓 → 決勝卓（2回戦）

## 5. ハマった罠

READMEにも技術的な罠は書いてあるが、**特に再発しやすいものを再掲する**。

### 伸びしろの天井（`compMax`）は必ず保存する（重大）

毎回 `現在の完成度 + pot` で計算し直すと、天井が現在地について回って
際限なく上がる。全員がいずれ100に到達してしまう。
セーブに `compMax` を持たせること。

過去には `ceiling = 30 + pot*0.9` と書いて、完成されたS級（pot=5）の天井が34になり、
経験を積むほど弱くなる逆転も起きた。**`pot` は総合力ではなく「今からどれだけ伸びるか」。**

### ムラ(`variance`)で係数を振り直すとき `skill` を落とさない（重大）

落とすと未熟なキャラも最善手を打つようになり、**育成が完全に無効になる**。
症状が「完成度を上げても勝率が変わらない」なので、直したつもりで直っていないことに
気づきにくい。実際にこれで一度、測定をやり直している。

### 係数の傾きだけでは強くならない

押し引きや守備の重みを動かしても、打牌の順位はほとんど入れ替わらない。
最初の実装では完成度100と15が同じ強さだった。
**`skill`（完成度そのもの）を渡して、未熟なほど最善でない牌を選ばせる**のが効いた。
完成度15なら47%の確率で二番手・三番手を打つ。

### 各画面のセーブ読み込みは、知らない項目も残す

拾い直した項目だけを返すと、他の画面が保存した内容を消してしまう。
`Object.assign({}, s, {...})` の形にすること。
実際にチーム編成の内容が名鑑を開いた瞬間に消えた。

### 出走表より先に対局が始まる

`prepare`（枠を組む）と `runTournament`（打つ）を分けてある。
一緒にすると「組み合わせを決めています」の裏で麻雀が始まる。

### 副露手の和了判定

`decompose()` が常に4面子を要求していたため、鳴いた手が一切和了れず、
CPUが全員メンゼン打ちになっていた。**`4 - melds.length` 面子を要求するのが正しい。**

### SVGのメタ情報を正規表現で削ると壊れる

牌の絵を軽くしようとして図形まで巻き込み、全部の牌が×印になった。
`tiles/` は無改変で置くこと。

### ビルド時の module.exports 除去

`/if \(typeof module[\s\S]*?$/m` は複数行のexportブロックを消しきれず、
閉じ括弧だけが残って構文エラーになる。`build.py` は
「最初の `if (typeof module` から末尾まで丸ごと落とす」方式にしてある。

### 日本語の識別子

`const 有 = ...` と書いたところ空白が失われて `const有` になり、
実行時まで気づけないエラーになった。**識別子は英数字で書く。**

### GitHubのWebアップロードは日本語のファイル名を壊す

**症状：**README に書いてある `docs/引き継ぎ書.md` が存在しない。
`ls` すると `蠑輔″邯吶℃譖ｸ.md` という名前で並んでいる。

UTF-8のファイル名がCP932として読み直され、二重エンコードされた状態で
コミットされていた（コミットが「Add files via upload」なら、まずこれを疑う）。
中身のテキストは壊れないので気づきにくい。

**`git push` で上げれば起きない。** ブラウザのドラッグ＆ドロップで上げると再発する。
この件があったので、引き継ぎ書は `docs/HANDOVER.md` にリネームした。
README が「ファイル名は英数字のみにする」と書いているのは、まさにこれのこと。

### UIは対局をまたいで使い回される

`UI` はモジュールの singleton で、対局が終わっても値が残る。
`match.js` が新しい卓を組むときに戻していない覚えがあると、
**次の対局が前の対局の状態を引きずる。**

- `_tachieReady` … 顔の並びを組み直したかの合図。落とさないと
  **前の対局の面子の顔が並んだまま**になる
- `_sayAt` … 吹き出しを引っ込める基準にした捨て牌の数
- `_idleSeat` / `_idleKyoku` … 残っていると二戦目の一局目で
  席がたまたま一致したとき雑談が一度飛ぶ

いまは `UI.auto = false` の隣でまとめて戻している。
（`_tachieSeat` も同じ場所で戻しているが、顔を一枚ずつ差し替えるのを
やめた時点で `ui.js` からは使われなくなった。消しても動く残り物）
**顔やセリフまわりに「前回と同じなら何もしない」種類の覚えを足したら、
同じ場所に戻す行も足すこと。** 大会は連戦なので必ず踏む。

### 表紙は画面の高さに収める。ページスクロールに頼らない（2026年9月）

**症状：**PLiCyに投稿したら、表紙は出るのに下の「はじめる」が押せない。
画面外に出ていて、スクロールもできない。

原因は二つ重なっていた。

1. 表紙のcanvasは1200×900の4:3で、`#cover{width:100%;height:auto}` で
   出していた。幅760pxだと**表紙だけで高さ570px**になり、
   その下のボタンを画面の外へ押し出す
2. 押し出されたぶんはページスクロールで届くはずだったが、
   **PLiCyのプレイヤーは枠のスクロールを止めていることがある**

直し方も二段構えにしてある。

- `src/title.css` … `#cover` の `width`/`height` を `auto` にして
  `max-height` で挟む。canvasは置換要素なので縦横比を保ったまま縮む。
  引く値（幅560px未満は410px、以上は355px）は表紙以外の中身の実測値。
  **表紙を縮めてでもボタンを画面内に残す**
- `shell.html` … `body` を `100dvh` で固定し、`#scroll` の中だけを流す。
  **ページスクロールに頼らない。**画面を替えたときは
  `window.scrollTo` ではなく `#scroll.scrollTop` を戻す

**canvasはDOMに置いたまま、中身も描いたままにすること。**
サムネイルの撮影に要る。`display:none` にしたり縮退させたりしてはいけない。

#### 表紙には下限がある。そこから先は中身を落とす

縮め続けると題字が読めなくなる。**下限は150px**（表示高さを変えて実際に
見て決めた。題字はcanvasの118px＝高さの13%なので150pxで約20px。
130pxだと題字は読めるが副題が潰れ、80pxでは題字も読めない）。

下限に当たってなお入らないぶんは、`title.js` の `fitTop()` が
**あらすじ（`.ttLead`）→ ロスター（`.ttRoster`）の順で落とす。**
題字は表紙でしか見せられないが、あらすじは他でも読ませられる。

**メディアクエリで一律に隠していない。**同じ画面の高さでも、
セーブの進み具合で中身の高さが変わるため。新規のセーブはボタンが1つで
「事務所の様子」も無いので余裕があり、あらすじを消す必要がない。
あらすじは新規のプレイヤーにこそ要る文章なので、消さずに済むなら残す。
実測なので、書体が代替に落ちて行数が増えた場合にも効く。

実測では、あらすじが落ちるのは高さ480pxの進行済みセーブだけ。
ロスターまで落ちる条件は今のところ無い。

#### 収まったかを測るときは、スクロール位置に依存しない形にする

`getBoundingClientRect()` は見えている枠が基準なので、`#scroll` が下に
送られたまま測ると、ボタンが上にあるように見えて「収まっている」と
誤判定する。**設定画面から「戻る」で表紙に戻ったときに実際にこれが出た**
（設定画面は縦に長く、そこでスクロールした状態のまま測っていた）。
枠の中身の座標に直してから、枠の見える高さと比べること。

検証は幅360/760 × 高さ480/568/640/812 の8通りを、
**新規と「続きから」が増える進行済みの両方**で見ること（計16通り）。
進行済みのほうが厳しい。設定画面へ行って戻る往復も忘れずに。

### `Jansou.normalize()` は知らない項目を捨てる（重大）

READMEは「セーブは他画面の項目を消さない」と書いてあるが、
**`normalize()` は既知のキーだけでオブジェクトを組み直している**
（`const out = { ... }` の形）。だから **`normalize()` に足し忘れた
`parlor` のキーは、次のセーブで消える。**

**症状：**「月報は出るが全部0」「模様替えが保存されない」。
毎日の営業で `store.set` するたびに落ちるので、
一日ぶんだけは正しく見えることがあり、気づきにくい。

`parlor` に項目を足したら、**必ず `normalize()` にも足すこと。**
`tools/test-jansou.js` に「normalize を5回通しても集計が消えない」を入れてある。

### 月報は `<p>` の中に入る。`<div>` を混ぜると構造が壊れる

**症状：**数字は合っているのに、月報の見出しや行が中央寄せになる。

`ask()` も `showMonthReport()` も本文を `<p class="jnPopText">` に入れる。
**`<p>` の中に `<div>` を書くと、HTMLパーサがその場で `<p>` を閉じる。**
以降の要素が `<p>` の外（`.popupBody` の直下）に出てしまい、
`text-align:left` の継承が切れて `.popupBody{text-align:center}` を拾う。

日報の `.jnRepWrap` に「p の中に入れるので span で組む」と書いてあるのは
このこと。**月報も span だけで組む**（`display:block` はCSSで与える）。
実際にこれを踏んだので、`renderMonth` の出力に `<div` が無いことを
テストで見るようにした。

### 覆われた釦は「無限ループ」に見える（2026年9月・重大）

**症状：**ブラウザで営業を自動で回すと、ある日で止まる。
レンダラのCPUが90%前後で回りっぱなしになり、`page.evaluate` も返らない。
`pageerror` は一つも出ない。**無限ループとしか見えない。**

**実際は無限ループではない。**割り込みのポップアップ（卓の故障・ボトル勝負・
客カード）は画面ぜんぶを覆う。その下にある釦を Playwright の `page.click` で
押しに行くと、「覆いが退くまで」待ち続けて返らない。裏では：

- 再生の `requestAnimationFrame` が回り続ける → **CPUが上がりっぱなし**
- ドライバが `click` を `await` したまま進まない → **その後ろの `evaluate` も呼ばれない**

**「メインスレッドが詰まっているか」は、詰まっていない経路を一本用意して
確かめる。**`click` を待っている側から見ると、何もかも詰まって見える。

| 見るもの | 無限ループなら | 覆われているだけなら |
| --- | --- | --- |
| `Debugger.pause` のスタック | 回っている関数 | 毎フレームの描画（`step`） |
| 別経路の `evaluate(() => 1+1)` | 返らない | **即座に返る** |
| `elementFromPoint`（釦の中心） | 釦そのもの | **覆い（`DIV.popup`）** |

**直しかたは「覆われている間はその釦を `hidden` にする」。**
押せないのに見えている釦は、人にとっても嘘になる。
`JansouFloor.skipHidden()` がスキップ釦の出し入れを持っていて、
`tools/test-jansou.js` で固定してある。

自動で回すときは **`tools/drive-jansou.js`** を使う。
**押す順は「ポップアップが先、スキップは後」。**
経緯と手順は `docs/design/jansou/monthly.md` §13。

### 配信するツリーを取り違える（2026年9月）

**症状：**base と head を見比べているのに、何をやっても同じ結果になる。

`cd` した先で `python3 -m http.server` を立てたつもりが、
シェルの作業ディレクトリが戻っていて**別の木を配信していた。**
これに気づかず、比較を半日ぶん無駄にした。

確かめかたは一行。**比較を始める前に必ず通す。**

```
curl -s localhost:8765/jansou.html | grep -c dbgOld
```

その木にしか無い目印（ここでは確認ボタン `dbgOld`）の有無で見る。
`tools/drive-jansou.js` は自前でサーバを立て、配信するディレクトリと

### 分割版は `src/` を相対パスで読む

**症状：**`index.html` を開くと真っ白。表紙だけ出て何も動かない。

既定のビルドは CSS と JS を `src/` の外部ファイルとして読む。
だから **`index.html` を一枚だけ切り出して開くと何も読めない。**
配布のZIPに `src/` を入れ忘れたときも同じ見え方になる。

動作を確かめるときは、リポジトリ直下で

```
python3 -m http.server
```

を立てて `http://localhost:8000/` から開くこと。
画像やフォントの確認も、もともとこの手順が要る（§4）。

**フォントのパスに注意。**外部のままの `src/*.css` は `src/` から見て
`../fonts/` が正しく解決される。`build.py` が `url(../fonts/` を
書き換えるのは**埋め込むCSSだけ**で、外部ぶんまで書き換えると
フォントが読めなくなる。

### 手元のコピーからzipを作ると、リポジトリにしかない変更が消える

**症状：**zipを展開して上書きしたら、少し前に入れたはずの修正が消えている。

リポジトリ全体ではなく手元の作業コピーからzipを作ると、
その後にリポジトリ側だけで直した分が古い内容で上書きされる。
実際に `docs/HANDOVER.md` と `src/match.js` で起きた。

**上書きする前に「手元のファイル vs zipの中身」の差分を見ること。**
リポジトリにしか無い変更が消える形になっていたら、単純上書きではなく
三方向マージにする。土台（zipを作った時点のコミット）を base、
手元を ours、zipを theirs にすれば `git merge-file` が通る。

zipを作る側は、**ドキュメントを入れない**（コードだけにする）か、
作る前に `git pull` するのが確実。

### Windowsで `python build.py` が無言で終わる

**症状：**`build.py` を叩いても `index.html` が更新されない。
エラーも出ず、`Python` とだけ表示されて終わる。

Pythonが入っていないのではなく、`WindowsApps` にある
Microsoft Storeのスタブ（`python.exe`）に当たっている。終了コードは9009。

原因は**Pythonを入れる前に起動したターミナルの PATH を引きずっている**こと。
環境変数の登録自体は正しくても、実行中のプロセスには反映されない。
**ターミナル（やClaude Code）を再起動すれば直る。**

確認するなら `python -V` ではなく `where python` を見る。
`WindowsApps\python.exe` しか出てこなければこの状態。

**Macではこの罠は起きない。**スタブが無いので、入れたPythonにそのまま当たる。
ただし叩くコマンドは `python3 build.py` にすること。`python` は
入っていないか、入っていても2系を指すことがある。
`tools/make-font.py` も同じで、`python3 tools/make-font.py` で実行する。

### 顔写真の `.mkFace` を借りるときは `position` を上書きする（重大）

**症状：**雀荘を開くと、**ゲームの枠の外・ページの左上**に四角い顔写真が
一枚だけ貼り付く。丸くクリップもされていない。フロアの丸写真
（`.jnFlHead`）は正しく出ているので、そちらを疑うと外れる。

`.mkFace` は名鑑の札のための部品で、`meikan.css` が
`position:absolute;inset:0` を持たせている（札の中で img の z-index を
閉じ込めるための指定）。**この class を他の画面から借りると、
借りた先が `position:relative` でないかぎり、写真は行から抜けて
いちばん近い配置済みの祖先＝`body` の 0,0 に飛ぶ。**

雀荘のシフト表（`.jnRow`）がこれだった。`.jnRow .mkFace` は幅と高さだけを
上書きしていて `position` を戻していなかったので、
**契約している人数ぶん（全部盛りで14枚）が同じ 0,0 に重なり**、
いちばん上の一枚だけが見えていた。行の側も写真の場所が空くので、
高さが 56px ではなく 51px になっている（気づきにくい手がかり）。

借りる側は `position:relative;inset:auto` を書くこと。
`.mkFace` そのものは直さない——名鑑・スカウト・チーム・ポップアップは
どれも `position:relative` の親を用意した上で absolute を前提にしている。

**同じ形を他の画面でも探すなら、**`class="mkFace` を grep して、
親に `position:relative` があるかを一つずつ見る。
2026年9月時点で外していたのは `.jnRow` だけだった。

### フロアの名前札は、幅を測ってから置く

14人出勤すると名前札（`.jnFlTag`）が隣どうしで重なって読めなくなっていた。
**立ち位置（`staffSpotFor`）は必ずばらけているので、丸写真は重なっていない。**
札が席の間隔より広いだけなので、原因は上の 0,0 の件とは**別**。

`drawUi` は札を「作る → まとめて測る → まとめて置く」の三度に分けて、
重なったら段を下げる。ここで**幅を覚えてはいけない。**
丸ゴシックが届く前に測った値を持ち続けると、代替書体の幅のまま残って
判定が外れる（実際にこれで一組だけ重なりが残った）。
測るのを一度にまとめるのは、要素ごとに測ると版が組み直るため。

### 500KB制限は、外部ファイル化で外した（2026年9月）

PLiCyには **`index.html` が500KBまで**という制限がある。
公式FAQには載っていないが、実際に何度も弾かれている。

**この制限は `index.html` にしか掛からない。ZIP全体は2GBまで許される。**
`fonts/` と `img/` はもともと外部参照で問題なく動いていたので、
CSSとJSも `src/` から読む形にした。361KB → 約13KB。
**以後どれだけ足しても、この制限に引っ掛かることはない。**

**PLiCyで外部のCSS・JSが読めることを確認した（2026年9月・ゆう）。**
表紙が正しく描画され、サムネイルも撮れた。
一時は `title.css` / `title.js` だけ埋め込む保険を置き、
外部JSが弾かれたときのために一枚版（`--single`）も残していたが、
**どちらも役目を終えたので廃止した。**`build.py` は一本道になっている。

同じ投稿で、表紙の下のボタンが画面外に出て押せない問題が見つかった。
原因と直し方は下の「表紙は画面の高さに収める」を参照。

PLiCyの制約は README にまとめてある。残りの要点だけ再掲：

- **ZIPには `src/` を必ず含める**（分割版はここを読みに行く。§5）
- サムネイルは**canvasの中身しか撮らない**（表紙を `#cover` に描いているのはこのため）
- セーブは **localStorage のままでよい**（PLiCyが公式に推奨している）
- 説明文に「下ネタ」「エッチ」などの語が入ると**無条件でR15**
- アップロードは1日10回まで
