# 卓の自由配置と隣接コンボ — 設計（第二段）

`spec.md` §15 で先送りした「卓の自由配置」の設計。実装前に確認する文書で、
決めたことと、決めていないこと（§11）を分けて書く。

前提として崩さないもの:

- §1「先に全部計算・再生は演出のみ」。乱数は `prepareDay` で使い切る
- §5.3「帯の `pay` の合計が `sales` に厳密一致」
- **`computeDay()` の数値には触らない。** 配置は `sales` を1円も動かさない（§6）
- canvas は表紙の一枚だけ。フロアは SVG のまま

---

## 0. いま何が起きているか

卓は `layout(tables, floorW)` が**幅から列数を決めて**自動で並べている。

| 症状 | 原因 |
|---|---|
| 狭い幅（floorW < 180 → 2列）で卓の上2席が描けない | 卓8が4行になり、行の間隔が 28px に詰まる。上の席（16px）を置くと上の卓にめり込むので `tight` で席を省いている。帳簿は4席のまま |
| 卓8のとき3行目の卓とソファ・カウンターが同じ高さに並ぶ | 床 127px に3行（42px間隔）を詰めると3行目が y=137〜157。ソファ（y=134〜152）とカウンター（y=134〜154）は固定座標で、同じ帯に居る |

どちらも「卓と設備が別々の座標系で、重ならない保証が無い」ことから来ている。
**一つのマス目に載せて、席まで含めた足元を占有させれば両方とも消える。**

## 1. グリッド

### 1.1 決めたこと

| 項目 | 値 | 理由 |
|---|---|---|
| 論理フロア | **200 × 164 floor px。端末によらず固定** | 配置は帳簿（席の取り方・追い出し順・コンボ）に効くので、端末で変わってはいけない（§3） |
| マス目 | **8 px 角。24列 × 15行。原点 (4, 38)** | 幅 4+192+4=200、高さ 38〜158。壁 0〜34、巾木 35〜36、床の上端 1px を空ける |
| 卓の足元 | **7 × 5 マス（56 × 40 px）。席4つを含む** | 席込みで占有するので、置けた卓には必ず4席が描ける |
| 入口 | **10〜13列 × 13〜14行（x 84〜116, y 142〜158）。固定・動かせない** | いまの入口マット（`(floorW>>1)-16` から 32px）と同じ位置。到着の湧き点 (94,144) がこの中 |

卓の足元 56×40 の内訳。

```
+0   +1        +13            +43       +55
 .  [席L 12]   [ 卓 30 ]      [席R 12]   .      ← y +1〜16 に席、+17〜36 に卓
        +16 [席T1 12] +28 [席T2 12]           ← 上の2席は y +1〜16、卓は +17〜36
```

- 横は 1 + 12 + 30 + 12 + 1 = 56。隣の卓とマスを接して置くと客どうしの間は
  2px（いまは 4px）。スプライトの輪郭は 12px のうち 10px なので見た目は 4px
- 縦は 16 + 20 = 36 を 40 に収め、次の行の客の頭まで **4px**。いまの3行配置は 6px
- 席の座標は足元の左上から**固定オフセット**。`seatsOf(t)` の `tight` 分岐は消える

### 1.2 8卓＋ソファ＋カウンターが必ず入ること

3列 × 3行 = 9 スロットのうち、中央下だけ入口に当たる。

```
列  0      7      14     21  23
行0 [卓1  ][卓2  ][卓3  ][ 帯 ]
行5 [卓4  ][卓5  ][卓6  ][ 帯 ]
行10[卓7  ][ 入口 ][卓8  ][ 帯 ]    ← 中央下は入口（13〜14行）で潰れる
```

- 卓のスロット 8 ＝ `TABLE_MAX`。**卓8はこの並びでしか入らない**が、入る
- 右の帯（21〜23列 = 24px × 120px）にソファ（3×3）とカウンター（3×3）を
  縦に置ける。中央下の入口の上（7〜13列 × 10〜12行）にも 3×3 が2つ入る
- ソファ 30×18 とカウンター 31×20 は **幅 24px に詰めて描き直す**
  （ソファは座面2枚を 10px ずつ、カウンターはボトル4本を 5px 間隔で）。
  端の列は狭い幅で 1px 削れることがあるので、設置物のスプライトは
  足元の内側に 1px の余白を取る

### 1.3 通路

**通路は保証しない。** 歩行は入口から席への直線補間で（§5.4 の演出層）、
経路探索はしない。マスが空いていなくても客は着ける。

通路が要るのはスタッフの立ち位置だけ。いまは「目当ての卓の空席 →
通路（最後の卓の下）」なので、これを

1. 目当ての卓の空席
2. その卓の足元の**周囲1マスで、何も置かれていないマス**（左上から時計回り）
3. 近い卓の順に 1〜2 を繰り返す
4. どこも無ければ入口の脇

に置き換える。詰めて置くとスタッフが入口に溜まる。それが「通路を空ける」動機になる。

### 1.4 却下した案

- **狭い幅で卓を縦向きにする** … 足元が 6×8 になり、15行に1行しか入らない。席の向きも無い
- **端末の幅でマス目の数を変える** … 同じセーブでも端末で帳簿が変わる。§1 に反する
- **ピクセル単位の自由配置** … 重なり判定と隣接判定が曖昧になる。マス目のほうが操作も楽
- **狭い幅では席を2つにする** … 帳簿の4席と絵が食い違う。いまの症状そのもの

## 2. セーブと移行

### 2.1 形

```js
parlor.floor = {
  v: 1,
  items: [
    { id: 1, kind: 'table',   x: 0,  y: 0 },   // x,y はマス（列, 行）。左上
    { id: 2, kind: 'table',   x: 7,  y: 0 },
    { id: 9, kind: 'sofa',    x: 0,  y: 12 },
    { id: 10, kind: 'counter', x: 20, y: 12 },
    { id: 11, kind: 'plant',  x: 21, y: 0 },
  ],
  next: 12,        // id の採番
  mine: 2,         // 自分の卓（joinNight のとき）。無ければ null
}
```

- **`parlor.tables` は残す。** `computeDay` の入力、`TABLE_COST`、`utilOf` が
  読んでいる。`floor.items` の卓の数と一致させる責任は `normalize()` が持つ
- 卓の並び順（`items` の中の順）が `tableIdx` の番号になる。閉鎖卓（故障）は
  いままでどおり最後の番号
- 壁のもの（ネオン・指名パネル・ミラーボール・スタンド花・出勤パネル）は
  **床のマス目に載せない。** いままでどおり `interior` / `sign` から描く

### 2.2 `normalize()` の突き合わせ（毎回・冪等）

1. `floor` が無い、または壊れている → `autoPlace(parlor)` で作る（2.3）
2. 範囲外・重なり・入口に掛かる項目 → 取り除いて、空いている場所に置き直す
3. 卓の数 ≠ `tables` → 足りなければ `autoPlace` の順で足す。多ければ末尾から落とす
4. ソファは `interior >= 4` のとき必ず1つ、それ未満なら無し。カウンターは `interior >= 5` で同じ
5. `mine` が卓を指していなければ null

`Object.assign({}, s, {...})` で他画面の項目を残す（`HANDOVER.md` §5）。

### 2.3 既存プレイヤーの店の再現 — `autoPlace`

卓は §1.2 の 8 スロットを **1→8 の順**に埋める。設備は候補を順に見て最初に
空いている場所に置く。

| 設備 | 候補（順） | 卓6以下のときの見え方 |
|---|---|---|
| ソファ | (0,12) → (21,9) → (7,10) → 全マス走査 | 左下。いまの (3,134) とほぼ同じ |
| カウンター | (20,12) → (21,12) → (10,10) → 全マス走査 | 右下。いまの (floorW−34,134) とほぼ同じ |

卓7・8では行10に卓が入るのでソファは右の帯に逃げる。**「同じ高さに並ぶ」は
起きない。** 卓の縦位置はいまと数px ずれる（2行なら 61/113 → 55/95）が、
並び順と設備は同じ。

`autoPlace` は増設ボタンにも使う（買った卓が最初の空きスロットに現れて、
選択状態になる）。

### 2.4 売る・戻す

| 種類 | 撤去 | 戻る額 |
|---|---|---|
| 卓 | できる。ただし2つ未満にはできない | `TABLE_COST[tables]` の半額（いまの卓数の増設費の半分）。`tables` を −1 |
| ソファ・カウンター | できない（内装の一部）。動かすだけ | — |
| 観葉植物（§4） | できる | 半額 |

## 3. 狭い幅での縮退

論理フロアは 200 固定なので、`fit()` が返す `floorW` が 200 未満のときは
**見える範囲を切り取って、横にずらせる**（パン）。

| 枠の幅 | 倍率 | floorW | 隠れる幅 | 既定（中央）で隠れるもの |
|---|---|---|---|---|
| 760 | 4 | 188 | 12 | 両端 6px。左端の卓の左席が 1px 削れる程度 |
| 600 | 3 | 198 | 2 | 両端 1px。マス目の外の余白だけ |
| 380 | 2 | 187 | 13 | 760 とほぼ同じ |
| 360 | 2 | 177 | 23 | 左端の卓の左席が 7px ほど削れる |
| 320 | 2 | 157 | 43 | 左端・右端の席がほぼ隠れる |

floorW は `measure()` が枠から 6px 引いて `fit()` に渡した値（目安）。

- **パンの単位は floor px。** 画面では `scale` の倍数だけ動くので、
  ニアレストネイバーの整数倍が崩れない
- パンは `floorToScreen()` に足す。UI層（丸写真・ポップ・当たり判定）は
  すべてここを通っているので（§8）、追従は一箇所で済む
- 操作は「床の何も無いところをドラッグ」。マウス向けに両端に 8px の
  矢印ボタンも置く（狭い幅のときだけ出す）
- **再生中の自動カメラ（任意）** … floorW < 200 のときだけ、直近の到着の卓が
  見えるようにパン先を寄せる。表示層だけの処理で帳簿に影響しない。
  落ち着かなければ切る

**「客が画面に出ない」は「席が存在しない」から起きていた。** 席が必ず在って、
隠れているだけならパンで見える。それがこの縮退の線引き。

  型を変えることはしない

## 5. 隣接コンボ

### 5.1 判定

足元の矩形どうしの距離で決める。純関数 `JansouFloor.combos(floor)`。

```
gapX = max(0, B.x − (A.x+A.w), A.x − (B.x+B.w))
gapY = 同様
隣接 ⇔ max(gapX, gapY) <= 1        （角で触れる・1マス空きまで隣接）
```

1マス（8px）の隙間まで隣接に数える。ぴったり付けないと成立しないのは
タッチで置くには厳しい。項目の並び順に依存しない。

### 5.2 コンボ一覧

| 名前 | 条件 | 効く先 | 経路 |
|---|---|---|---|
| **くつろぎ席** | 卓 + ソファ | 滞在が長い（`dwell` ×1.4）。満席でも最後に立つ。退店時に **チップ 300円/人**（臨時収入）。その卓の客は常連の進みが +1 | `build`（dwellMul, evictRank, tip）／`settle`（visitsBonus） |
| **カウンター席** | 卓 + カウンター | 上客（マダム・観光客・社長）が空いていればここに座る。ボトル勝負の挑戦者に選ばれやすい（×1.5） | `build`（席の好み）／`pickChallenge` |
| **入口席** | 卓 + 入口 | 一見さん（段階0）が優先。滞在が短い（×0.7）。満席になったら**最初に立つ**。満卓札はここに出る | `build`（席の好み, dwellMul, evictRank）／表示層 |
| **静かな席** | 卓が他の卓とも入口とも隣接しない | 特別客（打ち師・師匠・記者・協会）と段階2以上の常連が優先。将来の師匠効果（§6.1）の置き場 | `build`（席の好み） |
| **花道** | 卓の両側（左右の席の外）に観葉植物 | 指名の演出が2倍（帯ごと1人まで → 2人まで、うち1人はこの卓の担当） | `build`（nominate） |
| **ラウンジ** | ソファ + カウンター | 賭かるボトルが一段上がる（上限6）。勝てば大きく、負ければ高くつく | `pickChallenge`（tier） |

一つの卓に複数が成立してよい。**席の好みが競合したら「入口席 → カウンター席 →
静かな席」の順に見て、あとは番号の若い卓**（乱数を使わない）。

### 5.3 既存の INTERIOR / AUTO / SIGN との住み分け

| 経路 | 動くもの | `computeDay` |
|---|---|---|
| `INTERIOR.mul` | 需要（客足） | 入力 |
| `AUTO.rot` | 回転（容量） | 入力 |
| `SIGN.pull` / `ev` | 新規客・イベント率 | 入力 |
| `buffs`（pull / closed） | 翌日の客足・卓数 | 入力（既存の副経路） |
| **配置コンボ** | **誰が座るか・どれだけ居るか・誰から立つか・チップ／ボトル／常連／指名** | **触らない。`guests` も `sales` も不変** |

三つの段階は「店全体の量」、配置は「卓ごとの質」。この線を守るかぎり
§4 の実測（2000日）はそのまま有効で、§5.3 の厳密一致もそのまま成立する。

**客足に効くコンボは今回入れない。** 入れるなら `computeDay` の入力に
`comboMul`（席ごとの需要係数）を足すことになり、それは §4 の再計測と
セットで別途判断する。

### 5.4 金が動くのはチップとボトルだけ

- チップは `bonus` の経路（祝儀・お忍びと同じ）。**帯の `pay` には混ぜない**ので
  §5.3 の検証は今のまま。上部バーは「臨時」側に足す
- 額は `prepareDay` でタイムラインから合計して `plan.tips` に持ち、`settle` が
  `extraMoney` に足す。再生層の `bonus` イベントはその演出。スキップと
  通常再生の一致は自動的に保たれる
- 大きさの目安：卓8のうち1卓がくつろぎ席なら、客の約1/8 × 300円 ≒ 場代の
  1〜1.5%。手応えのためのもので、経済の柱にはしない
- ラウンジは既存のボトルの段階を動かすだけ。臨時収入の仕組みは増えない

## 6. タイムライン生成への影響

### 6.1 席の数え方は変わらない

置けた卓には必ず4席あるので、`seatsN = 使える卓 × 4` のまま。
`computeDay` の `seats` も同じ。**配置は席の数を変えない。変えるのは席の選び方。**

### 6.2 `build` の入力

`opts.tableIdx`（番号の配列）を `opts.tables` に広げる。

```js
opts.tables = [
  { idx: 0, evictRank: 1, dwellMul: 1.0, tip: 0,   prefer: [] },
  { idx: 1, evictRank: 2, dwellMul: 1.4, tip: 300, prefer: ['sofa'] },      // くつろぎ席
  { idx: 2, evictRank: 0, dwellMul: 0.7, tip: 0,   prefer: ['stage0'] },    // 入口席
  { idx: 3, evictRank: 1, dwellMul: 1.0, tip: 0,   prefer: ['joukyaku'] },  // カウンター席
]
```

`JansouFloor.tableTraits(floor, tableIdx)` が純関数で作り、`prepareDay` が渡す。
`tableIdx` だけ渡されたら全部が既定値（テストとの互換）。

### 6.3 変わる箇所

| 関数 | いま | これから |
|---|---|---|
| `pickSeats(n)` | 同じ卓で n 席 → ばら | 型と段階に合う卓 → 同じ卓で n 席 → ばら。同点は番号の若い卓 |
| `evictOldest(n, t)` | `since` の早い順 | **`(evictRank, since)` の順。** 入口席から立ち、くつろぎ席は最後 |
| `leaveAt` | `t + dwell` | `t + dwell × dwellMul`。閉店でクランプ |
| `leaveNow` | `leave` + `pay` | くつろぎ席なら `bonus {label:'チップ', amount: tip × count}` も同時刻に置く。`pay` の額は変えない |
| `nominate` | 帯ごと1人 | 花道があれば2人まで。乱数の引き方は増えるが `prepareDay` の中 |
| `full` の札 | `tables[0]` | 入口席 → 無ければ番号0 |
| `summary.faces` | id, typeKey, favTalent | `combo`（座った卓のコンボ）を足す。`settle` の visitsBonus と `pickChallenge` が読む |

### 6.4 守られる不変条件（テストに足す）

- Σ`count` = `guests`、Σ`pay.amount` = `sales`（帯ごと）— 変わらない
- 占有 ≤ 席数、歩行 ≤ `MAX_WALK`、`swap` は満席か歩行枠が埋まっているときだけ — 変わらない
- **新規**：追い出しは `evictRank` の低い卓から。同じ rank なら `since` の早い順
- **新規**：上客の到着時にカウンター席に空きがあれば、必ずそこに座る（段階0 と特別客も同様）
- **新規**：チップの `bonus` はくつろぎ席の `leave` と同時刻・同じ客にだけ付き、
  額 = 300 × count
- 種を固定すると同じタイムライン。スキップ消化と通常消化で `store` が一致 — 変わらない

`opts.tables` を省いた既存のテストケースは、そのまま通る。

## 7. 配置画面のUI

### 7.1 入り方

雀荘画面の設備の段に **「模様替え」** を置く。営業中は押せない（`runDay` が
root を差し替えるので、そもそも出ない）。

押すと同じフロアが**編集モード**になる：

- 客とスタッフを消して空の店にする（壁はそのまま）
- カーペットの上にマス目の角を 1px の点で打つ（ピクセル層。`#baa692`）
- 設置物ごとに透明な当たり判定を足元の大きさで置く（客の当たり判定と同じ作り）
- 成立しているコンボの名札を卓の上に出す（UI層。小さな札）
- 床の下に**道具棚**：「卓を増設 ○○円」「観葉植物 20,000円」と
  「成立しているコンボ：くつろぎ席 ×1、カウンター席 ×1」の一行
- 「完了」で戻る

### 7.2 置く・動かす・売る

**タップで選んで、タップで置く**を基本にし、ドラッグも同じ関数に落とす。

| 操作 | 動き |
|---|---|
| 設置物をタップ | 選択（黄色の枠 `PAL.tableCall`）。床の下に操作の段が出る |
| 選択中に床をタップ | タップしたマスが**足元の中心**になるよう置く。範囲外なら内側に寄せる |
| 設置物をドラッグ | 追従して、離したマスに置く。動き 6px 未満はタップ扱い |
| 置けない | 赤い枠を一瞬出して元の場所へ戻す。ティッカーに「そこには置けません」 |
| 床の何も無いところをドラッグ | パン（§3）。**選択中でも同じ**（置くのはタップ、動かすのはドラッグ） |

操作の段：

- 卓 … 「自分の卓にする」（`floor.mine`）／「撤去（○○円戻る）」／「とじる」
- 観葉植物 … 「撤去（10,000円戻る）」／「とじる」
- ソファ・カウンター … 「とじる」だけ

置けるかどうかは `JansouFloor.canPlace(floor, item, x, y)` 一つで見る：
範囲内・他の項目と重ならない・入口に掛からない。

**動かすたびに保存する。** 「完了」は画面を戻すだけ。取り消しは要らない
（動かすのは無料で、戻せる）。

### 7.3 狭い幅

操作の段と道具棚はフロアの**下**に置く（重ねない）。フロアはパンで見る。
360px で「選ぶ → 置く → 撤去」が親指で通ることを検証項目にする。

## 11. 決めていないこと（確認したい）

1. **チップを入れるか。** 臨時収入の経路で場代には触れないが、金が動くのは事実。
   外すなら、くつろぎ席は「滞在・追い出し順・常連の進み」だけになる
2. **観葉植物を足すか。** 花道のためだけの小物。コンボを卓・ソファ・カウンター・入口の
   4つだけで始めるなら要らない
3. **卓の撤去を許すか。** 半額で戻す前提。許さないなら「動かすだけ」で、
   `tables` は増えるだけになる
4. **狭い幅の自動カメラ。** 入れるなら表示層だけ。入れないならパンは手動だけ
