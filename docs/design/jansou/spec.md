## 0. 何をするのか

いまの直営雀荘は「営業ボタン → 裏で計算 → 結果表がポップアップ」で、
店が見えない。これを **ガールズ雀荘のフロアを見せて、一日が流れるのを眺める**
形に作り替える。カイロソフト系の経営ゲームの手触りを目標にする。

作るものは大きく5つ。

1. フロアの俯瞰ビューと一日の再生（ドット絵）
2. 客タイプ24種と、段階的に名前が分かっていく常連システム
3. 客をタップして「これは誰か」を見る客カード
4. 代表が打てる4つの卓（ボトルを賭ける。金は賭けない）
5. ガールズ雀荘の内装と、設備を買い足して派手になっていく流れ

**この指示書はモックアップ画像とセットで読むこと。** 配色・レイアウト・
スプライトの形は画像が正。文章と食い違ったら画像を優先する。

添付画像:
- `girls-ivory.png` … フロア全景（完成イメージ）
- `floor-staff.png` … スタッフをフロアに配置した状態
- `staff-ab.png` … スタッフ表現のA案B案比較（**B案を採用**）
- `customer-types.png` … 客タイプ24種
- `customer-card.png` … 客カード（タップ時）
- `bottle-tiers.png` … ボトル6段階
- `bottle-dialog.png` … ボトル勝負ダイアログ
- `names.py` … 名前生成の参照実装（Pythonなのでjsに移植する）

## 1. 最重要の設計判断 —「先に全部計算、再生は演出のみ」

**乱数を使う処理はすべて再生開始前に確定させる。**

1. `runDay()` の頭で、いまと同じように `computeDay()` を回し、
   `pickEvent()` でイベントを引き、成長の着順ロールまで**全部先に決める**
2. その確定結果から「タイムライン」（時刻付きの演出イベント列）を生成する
3. 再生層はタイムラインを順に消化するだけ。**乱数を一切引かない**

こうする理由:
- **スキップしても倍速でも結果が完全に同一**になる（スキップ＝即時消化）
- 演出をいくら作り替えても数値バランスが壊れない
- テストは「タイムライン生成」の純関数だけ見ればよい

**例外は実対局に入る分岐だけ**（荒らし／ボトル勝負／`joinNight` の同卓）。
プレイヤーの選択と実プレイ結果が要るので、タイムライン上に「割り込み点」を
置き、そこで再生を止めて従来の流れを実行し、結果を受けて続きを消化する。

## 2. 守ること（既存の決めごと。破らない）

- **canvas は表紙の一枚だけ**（PLiCyのサムネイル制約）。フロアに canvas は使わない
- 新規ファイルは `build.py` の `CSS` / `JS` リストに**追記しないと取り込まれない**
- セーブは他画面の項目を消さない（読んだものを全部残して書き戻す）
- **日本語識別子は使わない**
- **画面に出す新しい文言を足したら `python3 tools/make-font.py` を実行し直す。**
  今回は文言が大量に増える（客タイプ名24種、性格ラベル、ボトル名、セリフ、
  生成される人名の姓40＋名40＋二つ名10）。入っていない字はその一文字だけ
  別書体になる。**とくに人名の漢字は要注意**（検証中に「鴉」が未収録だと判明した）。
  名前生成に使う全文字を、フォント生成の入力に必ず含めること
- `index.html` は直接編集しない。`src/` を直して `python3 build.py`
- ブラウザ検証は必ず `python3 -m http.server 8765` 経由（`file://` は canvas が汚染される）

## 4. 絵の作り方（ドット絵）

### 4.1 描画方式

フロアは **低解像度で描いて整数倍に拡大**する。基準解像度 **200×164**、
表示倍率は幅に合わせて可変（モックは5倍）。

canvas が使えないので、実装手段は次の順で検討すること:

1. **SVG に `shape-rendering="crispEdges"` で矩形を並べる**（第一候補）
2. CSS の `box-shadow` によるピクセルアート
3. どうしても厳しければ、事前に PNG スプライトを生成して
   `image-rendering: pixelated` で拡大

いずれの場合も **拡大は必ず整数倍・ニアレストネイバー相当**にすること。
補間が入るとドット絵が台無しになる。

**採用：1のSVG（決定・2026年9月）。**
24種を `<symbol>` に一度だけ展開し、フロアには `<use>` を並べる。
画面上の要素は客・スタッフ・卓・設備で50個程度に収まり、歩行は
`<g transform>` の更新だけで済む。canvas を一枚も増やさないので
PLiCyのサムネイル制約（README「タグとしてのcanvasは表紙の一枚だけ」）に
そもそも触れない。

2のbox-shadowは却下。1要素に何千もの影を持たせる方式で、再描画が
そのたび全域に及ぶ。歩行アニメと客タップが両立しない。

3は保険として残す。スプライトのデータ形式（1文字1ピクセルの
パレット添字文字列）と描画層の境界を切っておき、実機でノード数が
問題になったら、同じデータからオフスクリーンcanvasでシートを焼いて
`background-position` で貼る方式に差し替える。README が
「JSの中だけで使う、DOMに出さないcanvasは問題ない」と明記している。

**倍率の決め方（決定・2026年9月）**

モックは5倍・1000px幅だが、`src/style.css` の `#app` は
`max-width:760px`。200×164を整数倍で収めると760pxでも3倍（600px）止まり、
380pxの縦持ちでは1倍（200px）しか入らず、客が12×16pxになって
タップも判別もできない。**モックが実機の幅を考慮していない。**

そこで、倍率を可変にするのではなく**フロアの横幅を可変にする**。

- 倍率 `s` … `160*s <= 使える幅` を満たす最大の整数。**2〜4に丸める**
- フロア幅 `floorW` … `min(200, floor(使える幅 / s))`
- 高さは164で固定

| 使える幅 | 倍率 | floorW | 実寸 |
|---|---|---|---|
| 380px（縦持ち） | 2 | 190 | 380px |
| 600px | 3 | 200 | 600px |
| 760px（PC上限） | 4 | 190 | 760px |

整数倍を守ったまま横幅を使い切れる。floorW が190〜200で揺れるぶんは
卓のグリッド配置が吸収する。

### 4.2 二層構造

カイロソフト系と同じく **ピクセル層＋くっきりUI層**の2層に分ける。

- **ピクセル層**: 床・壁・卓・客・スタッフの体・ネオン・設備
- **UI層**（等倍のDOM/テキスト）: 上部バー、金額ポップ、満卓札、
  ティッカー、客カード、ダイアログ、スタッフの丸写真と名前札

ドットの世界に日本語テキストを直接置くと潰れて読めない。文字は必ずUI層。

**カーペットはアイボリーだが明度は抑える**（`#d4c6b2` 前後）。
明るすぎると目が痛く、ドットのきらめきも飛ぶ。検証で確認済み。

床が明るいので、卓の照明は「明るくする」のではなく
**わずかにピンクを差す**処理にする（加算すると白飛びする）。

### 4.4 客スプライト

**12×16ドット、3頭身。** 顔が6px幅とれるので表情が出る。

構成: 濃茶のアウトライン → 顔 → 髪（前髪1段＋側面） → 目（2px、白ハイライト）
→ ほお紅 → 体（制服/私服） → 手 → 足。
足の位置を左右入れ替えるだけで歩行2フレームになる。

タイプの描き分けは **シルエット（帽子・髪型）＋色＋持ち物** の3点セット。
色だけで分けると小さくて判別できない。詳細は `customer-types.png` を見ること。

床が明るいので、**全スプライトの足元に楕円の影**（`#b29e8c`）を敷く。

### 4.5 スタッフ（雀ドル）の見せ方 — B案を採用

**丸写真の頭（実写・金縁）＋ドットの体（ピンクの制服・金の襟と帯）。**

丸写真だけだと床に浮いて、客と同じ世界に立っていないように見える
（`staff-ab.png` の左が却下したA案）。体を付けると歩けるし、
客と並んでも違和感がない。頭が大きいのはカイロ的な誇張として機能する。

- 頭: `img/{id3}.webp` を円形クリップ、金縁。**直径は 11 floor px**
  （`floor-staff.png` の金縁を実測して 57px÷5倍＝11.4）。
  CSSのpx固定にしないこと。倍率が可変なので `11 * scale` で出す。
  モックの「50px相当」は5倍表示での見え方の数字
- 体: 7px単位で 8×7 ドット。ピンクの制服 `#e84896`、金の襟と帯、両脇に手
- 名前札: 体の下にUI層で。**実キャラ名を使う**（`characters.js` の `name`）
- 指名が入っている子は頭の右上にハート（♥はフォント未収録なので図形で描く）
- 状態は3つ: 卓のそばで接客中／通路を歩行中（足入れ替え＋足元に土埃）／同卓中

壁の出勤パネルは**残す**。フロアの丸写真は「今どこで何をしているか」、
壁パネルは「今日の出勤メンバー」で役割が違う。

### 4.6 フォント

**すべての文字を丸ゴシック（`fonts/maru-ui.woff2`）で出す。** ゴシックだと
事務的で、ガールズ雀荘の空気にもドットのポップさにも合わない。

この書体は1ウェイトしかない。太字が要るところは縁取り（stroke）で太らせるが、
**小さい字を太らせると潰れる**ので 18px 相当以上に限ること。

`♥` `★` `×` はフォント未収録。**図形で描く**（ハート＝円2つ＋三角、
星＝10点ポリゴン、バツ＝線2本）。

## 5. 一日の再生

### 5.1 時間の設計（1倍速）

昼14秒 / 夕14秒 / 夜18秒、幕間1秒 → 一日およそ48秒。
倍速 ×1 / ×2 / ×4、スキップあり。速度は `parlor.speed` に保存（既定1）。

### 5.2 タイムラインのイベント種別

| 種別 | 内容 |
|---|---|
| `slotStart {key}` | 時間帯の見出し、照明の切り替え |
| `arrive {slot, typeKey, guestId, seatHint}` | 客が入口から歩いて空席に着く |
| `pay {amount, tableIdx}` | 卓の上に「+2,600円」がポップ、売上カウンタ加算 |
| `leave {guestId}` | 客が席を立って出ていく |
| `full {slot}` | 満卓の札（`day.slots[i].full` のとき） |
| `staffMove {charaId, to}` | スタッフが卓のあいだを歩く |
| `nominate {charaId}` | 指名が入る。頭上にハート、ティッカーに流す |
| `bottle {tier, charaId}` | ボトルが入る。売上加算＋ボトル棚の演出 |
| `interrupt {node}` | 割り込み点（実対局・選択肢） |
| `slotEnd {key, guests, sales}` | 帯の締め。幕間に「昼：4人 7,200円」を1行流す |
| `bonus {amount, label}` | 臨時収入（祝儀・お忍び・ボトル）。場代とは別のカウンタ |
| `dayEnd` | 閉店。残っている客が一斉に帰る |

`arrive` は §5.4 で人数（`count`）と演出モード（`mode`）を持つ形に広げた。

### 5.3 数値の展開ルール

- 各時間帯の `guests` 人ぶんの `arrive` を、帯の時間内に
  **前半やや疎・後半やや密**で散らす
- `pay` は一人一回、`fee` を基本にしつつ、
  **帯の合計が `day.slots[i].sales` に厳密に一致するよう最後の一人で端数調整**
- 席の管理は見た目の整合だけでよい。空きが無ければ入口で待たせ、
  `leave` の後に着席させる。延べ人数の厳密な収支は追わない
- `shugi` / `oshinobi` の臨時収入は該当帯の途中に演出として混ぜる
- **`joinNight` が有効なとき、夜の売上は `computeDay` が既に自分の卓のぶんを
  引いている。再生側で二重に減らさないこと**
- **上部バーの「本日」は場代と臨時収入の2本立てにする。**
  `day.slots[i].sales`（場代）に厳密一致させるカウンタと、
  ボトル・祝儀・お忍びを足す臨時収入のカウンタを分ける。
  混ぜると §5.3 の厳密一致が検証できなくなる

### 5.4 密度の設計（決定・2026年9月）

**実測。** `computeDay()` を400日回した帯ごとの延べ客・席・回転率と、
群のタイプで束ねたあとの到着イベント数。

| 局面 | 帯 | 延べ客 | 席 | 回転率 | 到着間隔 | 束ね後 |
|---|---|---|---|---|---|---|
| 序盤（卓2） | 昼 / 夕 / 夜 | 4.5 / 6.3 / 13.7 | 8 | 0.57 / 0.78 / 1.71 | 3.1 / 2.2 / 1.3s | 4.1 / 4.4 / 14.0件 |
| 中盤（卓4） | 昼 / 夕 / 夜 | 23.2 / 28.0 / 34.0 | 16 | 1.45 / 1.75 / 2.13 | 0.60 / 0.50 / 0.53s | 17.9 / 18.7 / 34.0件 |
| 終盤（卓8） | 昼 / 夕 / 夜 | 72.0 / 67.0 / 82.0 | 32 | 2.25 / 2.09 / 2.56 | 0.19 / 0.21 / 0.22s | 55.8 / 44.1 / 82.0件 |

**束ねは夜に効かない。** カップル（夕）・ママ友（昼）・サークル（夜に出ない）は
どれも夜のタイプではなく、いちばん密な夜は82件のまま。昼夕でも20〜35%しか
削れない。**束ねは味であって、密度問題の解ではない。**

**問題の本質は「延べ人数」を「入店シーン」として描こうとしていること。**
延べ82人は「32席が2.5回転した」という事実であって、82人の入店ではない。
`joinNight` で席が4つ減る序盤の夜は 13.7÷4＝3.4回転で、序盤から
すでに「見た客数＞席数」になっている。

#### 三つの層

| 層 | 中身 | 速度・演出で変わるか |
|---|---|---|
| **帳簿層** | タイムライン。`arrive`（人数つき）・`pay`（金額つき）・`leave`。Σcount＝guests、Σamount＝sales を厳密に満たす | 変わらない。テストはここだけ見る |
| **演出層** | 各 `arrive` を歩いて入れる（`walk`）か、席で入れ替える（`swap`）か。**ビルド時に確定**して `mode` として持つ | ビルド時に密度で決まる。再生は読むだけ |
| **表示層** | 金額ポップ・カウンタ・ティッカー | 速度で束ね方が変わる |

§1 はこの分離そのもの。乱数はビルダーが種つきで使い切り、再生は `mode` を
読んで描くだけ。**スキップ＝帳簿層を即時消化**で、演出層と表示層は素通り。

#### タイムラインの組み方

ビルダーは一日ぶんの席の占有を**ひとつの模擬**として通しで組む
（帯をまたいで座り続ける客がいてよい）。

1. **席数** `seats = (卓数 − 閉鎖卓 − 自分の卓) × 4`
2. **到着イベント** — 型を重みで引き、群のタイプなら人数ぶん消費。
   残りが人数に足りなければ群でない型を引き直す（「カップル1人」は作らない）。
   イベント数 N が決まったら `t_i = D × ((i + 0.5) / N) ^ 0.8`。
   指数0.8で前半やや疎・後半やや密
3. **滞在と退店** — 滞在の上限 `dwell = clamp(D × seats / guests × 0.85, 2.0s, 帯の残り)`。
   **満席時の到着は、最も早く座った客を追い出す**（`leave` を到着と同時刻に置く）。
   回転はこの追い出しで自然に出る。滞在は上限であって保証ではない
4. **支払い＝退店時。** `pay` は到着イベント1件につき1つ、`amount = fee × count`。
   帯の最後の `pay` に端数を寄せて Σ＝sales を厳密に合わせる。
   **退店時にするのがこの設計の要**（序盤は拍が倍になり、終盤は
   「客が立つ→金が上がる→次が座る」の連なりが回転の絵になる）
5. **演出モード** — その時刻に歩いている組が **`MAX_WALK`（3）組未満**で
   （群は連れ立って歩くので1組と数える。人で数えると4人のサークルが一生歩けない）、
   かつ空席がある（または歩行時間ぶん前に空く）なら `walk`（`WALK_SEC`＝1.5秒）、
   それ以外は `swap`（0.3秒。退店客が立ち、新客が座る）。
   歩行中の人数は×1基準のタイムライン秒で数える。**ここで決めたら以後変えない**
6. `slotStart` / `slotEnd`（幕間の締め1行）/ `full`（占有が席数に達した最初の時刻、
   `day.slots[i].full` のときだけ）/ `staffMove`（種から2.5〜4秒間隔で、直近に客が
   着いた卓へ）/ `nominate`（**演出のみ**、種から。第三段の指名への前振り）/
   `bonus`（祝儀・お忍びは該当帯の途中）/ `interrupt`（荒らし＝夜の6秒、
   `joinNight`＝夜の1秒。ゲストのもてなし・故障の選択肢もここ）/
   `dayEnd`（残っている客が一斉に帰る）

```js
{ t, kind:'arrive', slot, guestId, typeKey, count, table, seat, mode:'walk'|'swap', evict }
{ t, kind:'pay',    slot, guestId, amount, table }
{ t, kind:'leave',  guestId }
```

#### 同時歩行の上限と、溢れたぶん

**上限3組、歩行1.5秒（×1）** → 歩いて入れるのは毎秒2組まで。序盤は全員歩き、
中盤は夜の後半が `swap`、終盤は6割が `swap`。
**溢れたぶんは「もう座っている」として描く。** 入店シーンを見せない客は、
席の入れ替わりとして見せる。これで延べ82人が「32席が忙しく回っている」絵になる。
**入口の待ち客は最大2人まで描き、それ以上は描かない。** 行列は「繁盛」ではなく
「回っていない」に見える。上限と歩行秒は定数にしてある。

#### ×2・×4

**速度は時計の倍率であって、演出の切り替えではない。** モードはビルド時に
密度で決まっているので、速度で切り替える必要がない。終盤はもともと6割が
`swap` なので、×4 にすれば「席がめまぐるしく入れ替わり、ポップが束で上がる」
絵に自然になる。速度で変わるのは表示層だけ：

| 要素 | ×1 | ×2 | ×4 |
|---|---|---|---|
| 歩行 | 1.5s | 0.75s | 0.375s |
| `swap` | 0.3s | 0.15s | 即時 |
| 金額ポップ | 1件ずつ | 同じ卓で実時間0.5秒以内なら「+2,600円 ×3」に束ねる | 同左 |
| ティッカー | 全部流す | 客1人ずつの行は落とし、指名・ボトル・満卓・割り込みだけ | 同左 |

再生層に密度の条件分岐を持たせないのは、§1 の「再生は読むだけ」を守るためと、
スキップとの結果一致テストを単純にするため。

#### 序盤のスカスカ

昼14秒で4.1件は薄いが、**尺は変えない。** 一日48秒は「今日の営業」の体感長さとして
プレイヤーが学ぶリズムで、序盤だけ短いと後で伸びたように感じる。埋めるのは中身。
昼14秒に入る拍は、到着4.1＋支払い（退店時）4.1＋スタッフ移動4前後＋
開店・満卓・幕間の締め2〜3 ＝ 14〜15拍、**約1秒に1拍**。

拍と拍の間は**乱数なしの常時アニメ**で埋める。座っている客は席番号を位相にして
1.2〜2秒周期で打牌の手を動かし、スタッフは接客中に体を揺らし、ミラーボールは回り、
ネオンは瞬く。**すべて時刻だけから決まる。** ここに乱数が混ざると
スキップとの一致テストが崩れる。

```js
  weight: 10,            // 出現の重み
  personality: 'ねばる', // 性格ラベル
  effect: {...} }        // ゲーム上の効果
```

### 6.1 とくに重要な3タイプ

**推しファン** — 推しの雀ドルが出勤している日だけ来る。好感度（`favor`）が
上がるほど人数が増える。**これがあると「誰を出勤させるか」が売上に直結し、
育成と経営が噛み合う。** 現状は出勤者が係数を上げるだけなので、ここを繋ぐ。

**ただし売上への反映は先送りする（決定・2026年9月）。**
`computeDay()` が返す `sales` は §1 と §5.3 で「先に確定・厳密一致」に
縛られているので、再生層からは1円も動かせない。効かせるには
`computeDay()` の**入力**に favor 由来の項を足すしかなく、それは
`docs/HANDOVER.md` §4 の調整済み数値を動かすため、2000日の再計測が要る。
**絵が動く前にそこへ手を出すのは順番が逆。**

第三段で作るのは「推しが出勤している日に推しファンが現れる」という
**見た目と客カードの表示だけ**。人数と売上の連動は、再計測とセットで
後日あらためて行う。

**引き抜き屋** — 他事務所のスカウト。放置すると雀ドルの `favor` が下がる。
雀荘が「金を稼ぐ場所」から「事務所の防衛の場」になる。

**師匠** — 同卓した雀ドルの `addExp` が大きく進む。雀荘が育成施設になる。

### 6.2 効果の実装方針

第一段では**演出と客カードの表示まで**を作り、効果は次の3つだけ実装する:
**荒らし**（既存イベントと接続）、**常連の主**（後述の昇格の到達点）、
**推しファン（見た目のみ。§6.1 のとおり売上には反映しない）**。
残りは `effect` を定義だけしておき、第二段で有効化する。
**一度に全部繋ぐとバランスが崩れて原因の切り分けができなくなる。**

上限200人、超えたら訪問回数の少ない順に落とす。

## 9. 代表が打てる4つの卓 — ボトル勝負

**金は賭けない。負けたほうが「ボトルを入れる」。**
代表が勝てば客がボトルを入れて売上になり、負ければ店が一本おごって在庫が減る。

`bottle-tiers.png` / `bottle-dialog.png` が仕様。

### 9.1 4つの卓

| 呼ばれ方 | 客 | 賭かるもの | 勝てば／負ければ | 断ると |
|---|---|---|---|---|
| いつもの人と一局 | 常連の主 | ビール | 忠誠が上がる／失うものなし | 何も起きない |
| 名指しの果たし状 | 代表指名客 | ハウスボトル〜日本酒 | 評判が大きく伸びる／評判が下がる | 評判が少し下がる |
| 黙らせる一局 | 荒らし・酔っ払い | 相手の言い値 | その場で追い出せる／客が帰り売上が飛ぶ | 用心棒・警察など別解あり |
| ボトルを賭ける | デカピン客・社長 | ワイン〜タワー | 客が入れる（大きい）／店がおごる（在庫−1） | 何も起きない |

**危険度の階段になっている。** 序盤は常連と気軽に打ち、評判が上がると
指名客が来て、店に余裕が出てから高い酒に手を出す。
最上位は完全任意なので、堅実にやりたいプレイヤーは一生無視できる。

### 9.2 ボトル6段階

| # | 名前 | 売上 |
|---|---|---|
| 1 | ビール | 12,000円 |
| 2 | ハウスボトル | 30,000円 |
| 3 | 日本酒 | 60,000円 |
| 4 | ワイン | 120,000円 |
| 5 | シャンパン（ドンペリ） | 300,000円 |
| 6 | シャンパンタワー | 800,000円 |

**常連の格が上がるほど賭かるボトルの格も上がる**（段階0-1はビール止まり、
段階3の主はワイン以上）。常連育成がそのまま勝負の格上げになる。
タワーは年に数回の大一番のみ。翌日以降の来客が増える `buffs` を積む。

### 9.3 歯止め（必ず入れる）

- **代表が打てるのは1日1回まで。** 実対局は1回で数分かかる。無制限だと
  「営業を眺める」テンポが完全に壊れる。ダイアログに残り回数を明記する
- **迷惑客には打たない解決策を残す**（用心棒を雇う・警察を呼ぶ）。
  麻雀が苦手なプレイヤーが詰まないように
- 断っても評判が下がるのは「名指しの果たし状」だけ

### 9.4 実装

既存の `playOrSimulate(table, title)` にそのまま繋ぐ。
荒らし戦は既存の `ev.kind === 'arashi'` の処理をボトル賭けに置き換える
（`ARASHI_STAKE` の金銭授受をボトル在庫と売上に差し替え）。
勝敗判定は既存と同じく `rank.find(r => r.chara.id === 0)` の着順比較。

**荒らしの発生経路はひとつだけにする（決定・2026年9月）。**
`pickEvent()` の `ev.kind === 'arashi'`（重み16）が**唯一の発生源**で、
§6 の客タイプ「荒らし」は**その見た目の表現**として扱う。
客タイプ側から独立に湧かせないこと。同じ日に荒らしが2人出る。

**賭かるボトルは段階3〜4（日本酒60,000円〜ワイン120,000円）に対応させる。**
「相手の言い値」なので相手の格で段階を選ぶ。現状の
`ARASHI_STAKE = 100,000円` と桁を揃えるための決定で、
ビール（12,000円）に落とすと期待損益が約1/8に縮んでしまい、
荒らしという事件の重さが消える。

在庫: `parlor.bottles = [0,0,0,0,0,0]`（段階別の本数）。
`normalize()` に既定値を追加。おごるとき在庫が無ければ仕入れ費を引く。

### 9.5 決定事項（2026年9月・第四段の実装で決めたこと）

- **勝ち負けとボトルの動き**：勝てば客がボトルを入れ、**売値が臨時収入**になる
  （在庫は減らない）。負ければ**店がおごって在庫 −1**。在庫が無ければ
  **仕入れ値（売値の約1/3）を引いて出す**。金を賭けるダイアログは無い
- **挑戦者は一日に多くて一組**（`pickChallenge`、乱数は `prepareDay` で先に）。
  荒らしは `pickEvent` が唯一の発生源のまま、言い値だけ段階3〜4に決める。
  **型を先に見る**：段階3の社長は「いつもの人」ではなく、タワーを賭ける大一番の候補
- **1日1回**：`results.challenged` と `parlor.challengedToday`。二組目のダイアログは
  「受けて立つ」が押せず「今日はもう打ちました」と出る。エース・用心棒・警察・主は
  代表が打たないので回数に数えない
- **迷惑客の別解**：エースに任せる（自動）／**主に任せる**（段階3の常連が居る日だけ・無料）／
  **用心棒を呼ぶ**（30,000円）／**警察を呼ぶ**（評判 −2）。断って評判が下がるのは果たし状だけ
- **常連の主の効果**：**荒らしを追い返す**（上の「主に任せる」）と**客を呼ぶ**
  （既存の `buffs` の `pull` で翌日の客足に +4%、三人まで。取材と同じ経路で
  `computeDay` 本体には触らない）。主に勝つと来店回数が +2 進む（忠誠）
- **推しが辞めたとき**：常連の推しファンの `favTalent` が所属に居なければ、
  その日の出勤者から選ばれた推しに**乗り換える**（結果に一行出る）。
  出勤していないだけの日は、その日だけ別の子を目当てにして `favTalent` は変えない
- **在庫の仕入れ**：設備の下に「ボトル在庫」の段。段階ごとに1本ずつ仕入れる

## 14. 進め方

一度に全部作らない。この順で、各段階で動く状態にしてからコミットする。

1. **フロアが描けるところまで**（静止画。客・スタッフ・設備を配置するだけ）
2. **一日の再生**（タイムライン生成＋再生＋スキップ・倍速）。ここで
   スキップと通常再生の結果一致をテストする。

   **着手前に「密度」の設計を出すこと。** `computeDay()` を400日回した実測で、
   時間帯あたりの客数は序盤4.5人〜終盤82人と**18倍の開きがある**
   （序盤 卓2：昼4.5／夕6.2／夜13.7、計24.4人。
   終盤 卓8：昼72.0／夕67.0／夜82.0、計221.0人）。
   §5.1 の尺は昼14秒／夕14秒／夜18秒の固定なので、終盤の夜は
   **0.22秒に1人**、×4速では**毎秒18人**が入店する計算になり、
   個別の歩行演出は成立しない。逆に序盤は14秒で4.5人とスカスカ。
   カップル2人・ママ友3人・サークル4人で `arrive` を束ねる、
   同時歩行数に上限を設けて溢れたぶんは着席済みで出す、といった案を
   含めて、**序盤24人と終盤221人が同じ尺で見られる形**を先に決める。
   §5.3 の「席の管理は見た目の整合だけでよい」がこれを許している
3. **客タイプと名前・常連**（客カードまで）
4. **ボトル勝負**（4つの卓）
5. **内装の段階反映**

各段階の終わりに `python3 build.py` を通し、`tools/make-font.py` を
実行し直すこと（`pip install fonttools brotli` が要る）。

**`index.html` の500KB制限はもう気にしなくてよい（2026年9月）。**
CSSとJSは `src/` のまま読む形になり、`index.html` は約13KBで頭打ち。
PLiCyで外部のCSS・JSが読めることも確認済みで、一枚版（`--single`）は
廃止した。ドット絵のデータをどれだけ足しても上限には掛からない。

### 10.1 段階の対応（決定・2026年9月）

**数値（`mul` / `rot` / `pull` / `ev`）は変えていない。**引き継ぎ書 §4 の実測が

|---|---|---|---|---|
