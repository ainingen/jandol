# 月末決算・月報 — 設計（第三段）

`spec.md` §15「月末決算・月報 — 第三段」。`CLAUDE.md`「次にやること」の1番目。

**これは設計であって実装ではない。** レビューを通してから `src/` に手を入れる。

前段：`spec.md`（リニューアル全5段階・完了）、`placement.md`（自由配置3段階・完了）。
**この二つを読んでいる前提で書く。**

---

## 0. なぜ要るか

日々の営業は締まった。一日はフロアで流れ、収支が出て、閉店する。
**だが「先月どうだったか」を見る場所がどこにも無い。**

`parlor.log` は直近7日しか残らない。`parlor.total` は開店以来の通算で、
先月と今月の区別が無い。**その中間、「ひと月」の目盛りだけが抜けている。**

抜けていることで三つ困る。

1. **`spec.md` §12 で日報を簡略化した。** 時間帯別の内訳は再生で見せているので、
   日報からは帯を落とした。**一日ぶんは再生で見える。だが30日ぶんは誰も覚えていない。**
   帯の内訳が戻ってくる場所が要る
2. **常連が育っているのに、育った実感を返す場所が無い。** `parlor.regulars` は
   4段階で溜まっていくのに、いま何人居るかを出す画面が客カードしかない
3. **設備投資の判断材料が無い。** 卓を増やすか内装を上げるかは、
   一日のぶれ（±18%）越しには見えない。月単位でなら見える

## 1. 何を作らないか（先に線を引く）

**`spec.md` §15 の「連続時間化」には踏み込まない。**
月は**店の営業日を30回数えたもの**であって、ゲーム全体の暦ではない。
大会もスカウトも日を進めない。いまのままにする。

**経済のバランスに一切触らない。** 月報は**見せるだけ**。
月末のボーナスも、常連が売上を押し上げる仕組みも、この段では入れない。
`HANDOVER.md` §4 の実測（序盤 +3.3万／中盤 +10.6万／終盤 +26.1万）を
そのまま生かす。**測り直しが要る変更は、この段には一つも入れない。**

これは `spec.md` §6.2 と同じ判断。
「一度に全部繋ぐとバランスが崩れて原因の切り分けができなくなる」。

## 2. ひと月は30日

```js
const MONTH_DAYS = 30;   // wageOf() の salary/30 と対。片方だけ動かさないこと
```

恣意的な数ではない。`wageOf()` はすでに `BASE_WAGE + salary/30` と書いてある。
**日当は最初から「月給の三十分割」だった。**
30日で締めれば、30日ぶんの日当の合計がちょうど月給一人分に一致し、
月報の「人件費」が年俸表と突き合わせられる数字になる。

`wageOf` の `/30` も `MONTH_DAYS` を見る形に書き換える。
**値は30のまま**なので `HANDOVER.md` §4 の実測は動かない。

### 時計は `parlor.day` ひとつ

`parlor.day` は営業のたびに +1 される通し日数。**リセットしない。**
`log` も `total` もこれを基準に積んである。

「第何期か」「その月の何日目か」は `parlor.day` と `parlor.month.from` から
**導出する。** 別々に持つと必ずずれる。

```js
const inMonth = parlor.day - parlor.month.from;   // 0 始まり
const isMonthEnd = inMonth + 1 >= MONTH_DAYS;     // settle の中で判定
```

`day % 30 === 0` にしない理由は §6。

## 3. 何を見せるか

**七つの節。** 数字は書式の例で、実測前の仮の値。

### (1) 見出し

```
        第 3 期  決算
      61日目 〜 90日目
```

### (2) 場代の帯 — 時間帯ごと

```
昼  12〜17時    1,240人     1,984,000円  ████░░░░░░
夕  17〜21時    1,690人     3,549,000円  ███████░░░
夜  21〜26時    2,310人     6,006,000円  ██████████
─────────────────────────────────────
場代                       11,539,000円
```

**この三本の合計が場代に厳密一致する**（§7）。
`spec.md` §12 で日報から落とした帯が、ここで月の単位で戻ってくる。

**「売上」ではなく「場代」と書く。** `spec.md` §5.3 が
上部バーを場代と臨時収入の2本立てにしたのと同じ理由で、
言葉の段階で混ぜない。

### (3) 収支の帯

```
場代                       +11,539,000円
臨時収入                    + 1,180,000円
   ボトル 820,000 ／ チップ 210,000 ／ 祝儀・お忍び 150,000
日当（延べ 180人）          −  1,260,000円
家賃・光熱（30日）          −    600,000円
─────────────────────────────────────
今期の収支                 +10,859,000円      先期比 +18%
```

**四本の合計が収支に厳密一致する。** 臨時収入の内訳（ボトル／チップ／祝儀）は
一段下げて添えるだけで、帯として数えない。**帯は四本。**

ボトルとチップを分けて出すのは、`placement.md` §5.4 の
「チップは `bonus` の経路」という決めごとを**プレイヤーの側からも見えるように**
するため。模様替えでくつろぎ席を組んだ手応えが、月の額として返る。

```

今期の昇格   9人が顔なじみに、3人が常連に、1人が主に
```

**常連は新しく作らない。** `parlor.regulars` が

`spec.md` §7 が「常連化そのものがご褒美」と書いた設計の、月単位の受け皿になる。
客カードは一人ずつしか見えないので、**全体が育っている実感はここでしか返せない。**

**満卓だった日数**は、いまは再生中に札が出て消えるだけで残らない。
卓を増やすかどうかの根拠になる。

## 4. どの画面でどう出すか

### 営業の再生と地続き。新しいタブは作らない

30日目の閉店のあと、**日報の次にもう一枚**出す。

```
「今日の営業をはじめる」
   ↓
フロアで一日が流れる（スキップ・倍速）
   ↓
30日目の日報   [ 閉店する ]
   ↓
第3期 決算     [ 来月へ ]      ← ここが新しい
   ↓
雀荘の画面に戻る
```

理由：

- **月報は「場所」ではなく「瞬間」。** タブにすると営業と切り離され、
  見に行かれないまま古くなる。締めは営業の結末として出会うのが正しい
- 日報がすでに `ask()` の一枚でできている。**月報はその大きい版で、
  仕組みを一つも増やさずに済む**
- 「一回押す＝一日進む」というリズムを壊さない
- 新しい画面・ナビゲーション状態・現在地のセーブが要らない

### 読み返す入口

締めは流れてしまうので、雀荘の画面に

```
      ［ 先月の決算を見る ］
```

を置く。押すと**保存済みの月報（`parlor.months` の末尾）を同じ `ask()` で開く。**
**開き直しても数字は作り直さない。** 締めた時点の確定値を並べるだけ（§7）。

### 演出

- 帯は左から伸びる（CSSの `transition:width`）。節は上から順に現れる
- **全部で1.2秒ほど。どこかを触ったら即座に最終形へ飛ぶ**
- **数字は最初のフレームの前に全部確定している。**
  アニメーションは確定値へ向かうだけで、途中の値を計算しない

再生のスキップと同じ考え方（`spec.md` §1）。**待たせない。**

### canvas は使わない

`spec.md` §2「canvas は表紙の一枚だけ」。帯は `div` の幅で描く。
`jansou.css` の `.jnRepTrack` / `.jnRepFill`（評判のバー）と同じ作りを使う。

## 5. 三層のどこに置くか

`spec.md` §5.4 の**帳簿層 → 演出層 → 表示層**、
`runDay` の **prepareDay → playDay → settle** に対して、月の締めは

**`settle` の末尾（純関数・乱数を引かない）。**

```
prepareDay(rng)   乱数を全部使い切る          ← 触らない
playDay(plan)     割り込み（ask・実対局）      ← 触らない
settle(...)       純関数。ここに accrue と月の締めを足す
  ├ 既存の締め（profit・rep・buffs・log・regulars・bottles・total）
  ├ accrue(month, その日の確定値)      ← 足す
  └ isMonthEnd なら closeMonth(...)     ← 足す
showResult(...)   日報                       ← 触らない
  └ out.report があれば showMonth(report)  ← 足す
```

**月の締めを `playDay` に置いてはいけない。** 割り込みが入る層で、
乱数と実対局の結果が絡む。`settle` は既に純関数なので、
**そこに足せば「スキップしても再生しても完全一致」（`spec.md` §16）が自動的に守られる。**

月報の表示は `showResult` の後ろ。**`ask()` を入れ子にしない**
（`playDay` の割り込みと混ざる）。

## 6. 月をまたぐ処理

### 大原則：月末は「締め」であって「リセット」ではない

**空にするのは集計の入れ物（`parlor.month`）ひとつだけ。**

| 何を | 月をまたぐと | なぜ |
| --- | --- | --- |
| `day` 通し日数 | **持ち越す** | `log` と `total` の基準 |
| `rep` 評判 | **持ち越す** | 店の評判は月で消えない |
| `buffs` | **持ち越す**（減りかたも変えない） | 下に詳述 |
| `bottles` ボトル在庫 | **持ち越す** | 下に詳述 |
| `regulars` `seen` 常連 | **持ち越す** | 通った回数は月で消えない。§3(4) は数えるだけ |
| `floor` 配置 | **持ち越す** | 置いた物 |
| `shifts` `joinNight` `speed` | **持ち越す** | 毎月組み直させるのは手間なだけ |
| `tables` `interior` `auto` `sign` | **持ち越す** | 買った設備 |
| `log` 直近7日 | **持ち越す** | 月と無関係の直近履歴 |
| `total` 通算 | **持ち越す** | 生涯累計 |
| `challengedToday` | 日ごとに false（既存のまま） | 月とは無関係 |
| `month` 集計の入れ物 | **空にする** | **ここだけ** |
| 店の外（`money` `comp` `compMax` `grades` `favor`） | **持ち越す** | 触らない |

### buffs は月をまたいでもそのまま減る

28日目に「雑誌の取材（三日間 客足が伸びる）」が出たら、**31日目にも効く。**

- バフは**店に起きた出来事**であって、会計期間とは関係が無い
- 月末で切ると「取材は月末に来ると損」という妙な読みが生まれる
- 「卓の故障（明日は一卓閉める）」も同じ。月末に壊して逃げられないようにする
- 常連の主の `pull +4%`（`spec.md` §9.5）も同じ経路。切る理由が無い

**実装はいまのコードのまま。月末処理はここに一切触らない。触らないことが設計判断。**

### ボトル在庫は持ち越す。月報には「動き」だけ出す

`parlor.bottles = [0,0,0,0,0,0]` は段階別の本数（`spec.md` §9.5）。
勝てば売値が臨時収入（在庫は減らない）、負ければ在庫 −1、
在庫が無ければ仕入れ値（売値の約1/3）を引いて出す。

- **在庫は物であって金ではない。棚の本数は月末に消えない。持ち越す**
- **月報の帯に出るのは金の動きだけ** — 勝ったぶんの売値は臨時収入の
  「ボトル」に、在庫が無くて出した仕入れ値は**臨時収入の減として同じ経路**に入る
  （いまの `settle` がそう書いてある。**変えない**）
- **在庫の本数は帯ではなく、§3(6) のできごとに「12本（期首 8本）」と添える**

**在庫の本数を金額に換算して帯に混ぜないこと。** 混ぜた瞬間に
§7 の「帯の合計＝収支」が崩れる。`placement.md` §5.4 が
「チップを `pay` に混ぜると Σ`pay` ＝ `sales` がその場で壊れる」と
書いたのと同じ形の罠で、**在庫は同じ罠の二つ目の入口。**

### 月給を月末にまとめて払うのは「やらない」

月の概念ができると「日当をやめて月末に月給を一括で」が自然に見える。**やらない。**

- 合計は同じ（`salary/30 × 30`）だが、**現金の流れかたが変わる。**
  月末に大きな支出が来る形にすると、月初に設備を買ったプレイヤーが月末に破綻する
- `HANDOVER.md` §4 の実測は**すべて一日単位**で取ってある。測り直しになる

**日当は毎日払ったまま。月報はその合計を見せるだけ。**

## 7. 守る前提と、その検算

### `spec.md` §1「先に全部計算、再生は演出のみ」

月の締めは **`closeMonth()` という純関数に一度だけ集める。**
返る `report` を描画側はただ読む。

```js
/* 純関数。乱数を引かない。DOMを触らない */
function blankMonth(fromDay, parlor)            // 空の入れ物
function accrue(month, d)                       // 一日の確定値を足す。整数だけ
function closeMonth(month, prev, parlor, regs)  // → report を一度に作る

/* 描画。report を読むだけ */
function showMonth(report)
```

**守り方：`showMonth` の中に四則演算を書かない。**
帯の長さの `%` すら `closeMonth` が `report` に入れて渡す。
そうすれば「締めのとき」「読み返したとき」「アニメーションの途中」で
同じ数字が出ることが構造的に保証される。

**検算（`tools/test-jansou.js` に足す）：**
同じ `report` を二回 `closeMonth` に通して**深く等しい**こと。
`report` は乱数にも `Date` にも依らないこと。

### `spec.md` §5.3「帯の合計が sales に厳密一致」

**`month.fee`（場代）を独立した変数として持たない。帯の合計として定義する。**
`computeDay()` が `sales: slots.reduce(...)` と書いているのと同じ形。

```
月の場代 = Σ month.slots[k].sales            （k = 昼・夕・夜）
月の収支 = 月の場代 + extra − wages − util
```

積む値は**すべて整数**なので誤差が出ない
（場代は `guests*fee`、日当は `wageOf` が `Math.round`、家賃は `8000+tables*1500`、
チップは `TIP_PER_GUEST*人数`、ボトルは表の定数）。

**検算：**

```
Σ month.slots[k].sales        === month.fee            （一円まで）
fee + extra − wages − util    === Σ（その日の profit）  （一円まで）
Σ month.slots[k].guests       === month.guests
```

`settle` が返す `profit` を30日ぶん配列に取っておいて突き合わせる。
**平均や割合から逆算した数字を帯に混ぜない。**

### `computeDay()` の数値には触らない

**本体を一行も変えない。** 積み上げは `computeDay` が**返した後**、
`settle` の中で行う。`SLOTS` `INTERIOR` `AUTO` `SIGN` `BASE_WAGE` `utilOf` の
**値も変えない**。`wageOf` の `/30` は `MONTH_DAYS` を参照する形に書き換えるが値は30。

**検算：** `git diff src/jansou.js` で `function computeDay` の中に差分が無いこと。
`HANDOVER.md` §4 の三局面（序盤・中盤・終盤）を2000日回して、
**実装前と同じ数字が出ること**を確認する。

### `canvas` は表紙の一枚だけ

**検算：** `grep -c "<canvas" index.html` が 1。

## 9. 先に書いておく罠

### `normalize()` は知らない項目を捨てる（重大）

`README` は「セーブは他画面の項目を消さない」と書いているが、
**`Jansou.normalize()` は既知のキーだけでオブジェクトを組み直している**
（`src/jansou.js` の `const out = { ... }`）。

**`normalize()` に足し忘れた `parlor` のキーは、次のセーブで消える。**
`month` を足しても `normalize()` に書かなければ、
**一日営業するたびに集計が消えて、月報が永遠に0になる。**

症状は「月報は出るが全部0」。気づきにくい。**最初に `normalize()` を直すこと。**

### `parlor.log` から月を集計しない（重大）

`log` は `.slice(-7)` で**直近7日しか残らない。**
30日ぶんを合計しようとしても7日ぶんしか無い。
**月の集計は `parlor.month` に独立して積む。** `log` は表示用の別物。

### ボトル在庫の本数を帯に混ぜない

§6 に書いたとおり。`placement.md` §5.4 の
「チップを `pay` に混ぜると壊れる」と同じ形の罠。
**帯に出していいのは、その日 `settle` が確定させた金額だけ。**

### 月末の判定を `day % 30` でやらない

既存セーブは `day` が中途半端な値（47日目など）で止まっている。
`% 30` にすると、そのプレイヤーの初回の月報は
**13日ぶんしか入っていないのに「一ヶ月」として出る。**
`month.from` からの経過で判定する（§2 / §10）。

### 月報の中で `ask()` を入れ子にしない

月報は**表示だけ。何も起こさない。**
`playDay` の割り込み（実対局・選択肢）と混ぜると、
`HANDOVER.md` §4「おまかせ」の宙に浮いた Promise と同じ罠を踏む。

### `settle` は純関数のまま保つ

`closeMonth` を `settle` の中で呼ぶが、**`Math.random()` も `Date` も使わない。**
一つでも入れた瞬間に `spec.md` §16 の
「スキップしても再生しても完全一致」が壊れ、テストで検出できなくなる。

### `months[]` は放っておくと無限に伸びる

1年で12件、3年で36件。**`.slice(-12)` で直近12期だけ残す。**
生涯累計は `parlor.total` が別に持っているので情報は失われない。

### 縦横の両方で描画して確かめる

月報は日報より縦に長く、`.popupBox` からはみ出す。
`python3 -m http.server 8765` 越しに、**いちばん長くなる状態**で測る —
出勤12人・イベント全部・昇格あり・前期比あり・臨時収入の内訳3行。

## 10. 既存セーブの移行

いまのセーブに月の概念は無い。`parlor.day` は途中の値（47日目など）で止まっている。

### `month.from` に「今日」を入れる

`normalize()` で `month` が無ければ

```js
month: p.month || blankMonth(out.day, out)   // from = いまの day
```

こうすると、47日目のプレイヤーの第1期は**47日目から77日目までの、
まるまる30日ぶん**になる。

### なぜ後ろに寄せるのか

- `day % 30` だと初回が13日ぶんの半端な月報になる。**半端な数字を「一ヶ月」と
  名乗らせない**
- **過去は復元できない。** `log` は7日ぶん、`total` は生涯累計で、
  月に切り分ける材料がどこにも無い。**無いものを推定して出さない**
  （`HANDOVER.md` §9「数値は測ってから決める」の裏返し）
- 待つのは初回だけ。第2期からは全員が30日ちょうど

### 画面に出す

雀荘の画面に、`months` が空で `month.days > 0` のときだけ

```
      第1期の集計中   12 / 30日
```

を出す。**いつ月報が出るのかが分かる。**
第2期以降も同じ表示でよい（進捗として自然）。

### 期の番号

`months.length + 1`。既存プレイヤーの初回も「第1期」。
**日数から逆算して「第2期」などにしない** — 第1期の中身が無いのに
番号だけ進むと、月報の履歴に穴が空く。
