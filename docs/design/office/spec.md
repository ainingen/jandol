# 事務所ハブと日進行の統一 指示書

対象: https://github.com/ainingen/jandol
置き場所: `docs/design/office/spec.md`
先に `CLAUDE.md` と `docs/HANDOVER.md`（とくに §4 直営店の経済／§5 `normalize()` の罠）、
`docs/design/jansou/spec.md` §1（先に全部計算、再生は演出のみ）を読むこと。

---

## 0. 何をするのか

いまのゲームは雀荘だけが**日単位**で動き、大会とスカウトは**回数単位**で動いている。
時間軸が二つある。これを一つにする。

やることは三つ。

1. **事務所をハブにする。** 表紙から入ったら必ず事務所に着き、
   各画面へはそこから行き、必ずそこへ戻る。一日は事務所で始まり事務所で終わる
2. **雀荘の日をゲームの日にする。** スカウト・大会・アイドル活動が
   日を消費するようになる。代表が遠征に出ると店に立てない
3. **依頼が事務所に届く。** 大会の招待・契約イベント・アイドル案件は
   すべて「条件で発火する依頼」として同じ表に載る

これは `docs/design/jansou/spec.md` §15 で「今回の範囲外」とした
**「連続時間化（大会・スカウトとの時間整合を作り直す）」そのもの**。
雀荘が完成して宿題が無くなったので、ここで着手する。

コンセプトは表紙の一文に従う。
「全国の雀荘を歩いて雀ドルを見つけ、口説き、育てて、大会に出す。
最後は最強の八人「雀エイト」を、あなたの事務所で独占する。」
新しい要素はこの**見つける・口説く・育てる・出す**のどれかに対応させる。
どれでもないものは入れない。

## 1. 最重要の設計判断

### 1.1 代表の身体は一つ

すべての制約はここから出す。代表は**事務所（＝店）にいる**か**遠征に出ている**かの
二択。事務所の下に雀荘があるので、事務所にいれば卓に呼ばれてすぐ降りられる。
遠征中は降りられないので、代表戦は**留守を任せた雀ドル**が打つ。

代表が要るのは遠征だけ。アイドル活動・大会は雀ドルだけで行ける。
だから遠征と並行して留守番組が仕事をこなす、という配分が生まれる。

### 1.2 `parlor.day` がゲームの日。新しいカウンタを作らない

雀荘の `parlor.day` を全画面がそのまま読む。
`MONTH_DAYS` と `wageOf()` の30は対なので（HANDOVER §4）、別の日カウンタを
持つと月報がずれる。**店は毎日営業する**（遠征中も、代理で）ので、
「日を進める」＝「今日の営業を回す」でよい。

#### 店が無い日も、同じ締めを通す。日当は払う

**開店は今のまま。**50万を払うまで店は無い。
**弱小事務所なので最初は店を持てない**、が設計で、
「まず店を持つ」が序盤の最初の目標になる。

ただし **日は店の有無に関係なく進む。**店が無い日も、事務所の
「今日を始める」で `parlor.day` が進む。

やり方は「営業しない日」として**既存の締めをそのまま通す**こと。
卓0で `computeDay` を回せば客0・売上0になり、日は進み、日当は払われ、
月次の決算も（売上0で）出る。**日を進める場所を `settle` 以外に増やさない。**

- **店が無い日の昼は雀荘へ委譲しない。**事務所の中で
  「今日は営業していません」と一行出して夜へ。
  夜の日報は日当の支出だけが載る
- **家賃は掛からない**（`util: 0`）。家賃は店のもの
- **誰も出勤していない**ので、成長も月報の出勤も付かない。
  日当は出勤ではなく**契約に対して**払うので、所属の全員ぶん出ていく

これで店が無い期間にも所属の日当が出るようになる。
**序盤の収支が変わるが、いまは数字を触らない。第三段の再測に含める**（§11）。

### 1.3 終わりは無い。区切りはある

リリース後に依頼（イベント）を足していく運営を前提にする。だから

- **取り返しのつかない損失を置かない。** 疲労は回復しきる。離脱は必ず警告を挟む。
  遠征に失敗しても、日数と費用をまた払えば再挑戦できる
- **セーブは前方互換。** 未知のキーを消さない。欠けたキーは既定値で埋める
- **依頼は条件で発火し、日付で発火しない。** 後から足した依頼が
  新規プレイヤーにも100日進めた人にも同じように届くように

### 1.4 触らないもの

- **`Jansou.computeDay()` と `parlor` の経済。** HANDOVER §4 の実測がこれに乗っている。
  遠征中の店は「代表戦が代理になる」「`joinNight` が効かない」だけで、客数と場代は変えない
- **`Scout.evaluate()` と、`event` 以外の `RULES`。** 契約条件の判定は
  純粋関数として完成している。遠征はその**前に対局を挟み、
  判定の場所を現地にする**だけ。
  **`RULES.event` だけは第四段で書き換える**——依頼テーブルに条件を持たせ、
  `RULES.event` は「その依頼を受けたか」だけを見る形にする（§8.2）
- **`REGIONS`（六地方）。** `aisho`（同郷）と `area`（全地方）は地方のまま。
  県は地方の下に置く（§4）

- canvas は表紙の一枚だけ

### 3.1 実際の配線（2026年9月3日に読んで確かめた）

この指示書は配線の実装を知らずに書いてあったので、読んだ結果をここに残す。

**画面の切り替えは `shell.html` 末尾の IIFE にある `go(name)` 一つだけ。**
`index.html` は `shell.html` にタグを差し込んだだけなので、直すのは `shell.html`。

- `go(name)` は毎回 `#view` を空にして新しい `<div>` を作り、
  `Title/Meikan/Team/Taikai/Jansou/Scout` の `mount(root, store)` を
  `if/else` で呼び分けているだけ。**画面の後始末（unmount）の口は無い**
  （`title.js` だけが自前で `resize` を張り替えている）
- `go` を呼ぶ経路は6つ：起動時の `go('title')`、`store.onContinue`
  （`teamDecided` なら `taikai`、でなければ `team`）、`store.onStart` → `team`、
  `store.onDecided` → `taikai`、`#appHome` → `title`、`#appReset` → `team`
- 下のタブ `#nav` は `data-go` を持つ5つの釦。`paintTop()` が
  **`teamDecided` が立つまで `team` 以外を `disabled` にする**
- セーブの最上位は `shell.html` の `blankState()` / `loadState()` が持つ。
  **§10 の新しいキーはここに足す。**`loadState` は
  `Object.assign({}, s, {...})` なので知らないキーは残る（§10 の要求を既に満たしている）

**朝→昼→夜の乗せかた（採用した案）**

`go()` に段階を持ち込まない。**`office` を六つめの画面として足し、
朝／夜は `office.js` の内部状態にする**（`title.js` が `screen` で
表紙と設定を切り替えているのと同じ形）。昼は画面ではなく委譲で、
「今日を始める」が `go('jansou', { autoRun: true })` に相当する呼び出しをして
雀荘の営業を回し、終わったら事務所へ戻って夜を出す。

そのために `shell.html` の `go(name, opts)` に第二引数を足し、
`Jansou.mount(root, store, opts)` が `opts.autoRun` を受け取れるようにする。
フロアの描画は雀荘の DOM のままなので、演出は一行も動かさない。

公開インターフェース案:

```js
const Geo = (() => {
  // PREFS: [{ key, name, lat, lng, scale, region }] ×47
  function distKm(a, b) -> number            // 県key同士。対称
  function farOf(km) -> 0..5                 // 遠さの段階
  function prefsOf(region) -> [pref]         // 地方→県
  function prefOf(key) -> pref | null        // key→県。PREFS は配列なので添字では引けない
  return { PREFS, distKm, farOf, prefsOf, prefOf };
})();

const Office = (() => {
  function mount(root, store) -> controller
  // 純関数（テスト対象）
  function planTrip(st, pref, purpose, members) -> { days, cost, far }
  function assignOf(st) -> { [charaId]: 'parlor'|'trip'|'rest'|'job:<offerId>' }
  function deputyOf(st) -> charaId | null     // 代表不在時に代表戦を打つ子
  return { mount, planTrip, assignOf, deputyOf };
})();

const Offers = (() => {
  // TABLE: [{ id, kind, when(st, roster)->bool, once, prio, days, members, text }]
  function fire(st, roster) -> [offer]        // 今日新しく届くもの（once は fired を見る）
  return { TABLE, fire };
})();
```

## 4. 県と地方 — 二層にする

**見せる単位は47県、計算の単位は既存の6地方。**

| 層 | 単位 | 持つもの | 使う場面 |
|---|---|---|---|
| 県 | 47 | 座標・規模・所属地方 | 本拠地の選択、遠征の距離と費用、依頼の発生 |
| 地方 | 6（`REGIONS` のまま） | — | `aisho`・`area`・契約条件・発見の抽選（当面） |

県→地方の対応表が一枚あれば、既存ロジックは一行も変えずに地方で動き続ける。

### 4.2 距離と遠さ

`distKm` は球面距離でよい（緯度経度→km、1度≈111km の平面近似でも可）。
遠さの段階 `far` はkmを丸めた 0〜5:

| km | far |
|---|---|
| 〜80 | 0（同じ生活圏） |
| 〜250 | 1 |
| 〜500 | 2 |
| 〜800 | 3 |
| 〜1200 | 4 |
| それ以上 | 5 |

京都からだと、大阪0・名古屋1・東京2・福岡3・札幌4・那覇5。
**遠征の日数と費用は km ではなく far から出す**（§7.2）。段階にしておくと
数字を触るとき表一枚で済む。

### 4.3 「日数は移動ではなく滞在」と考える

現実の移動時間に忠実にすると日本はどこでも1日で着き、距離の意味が消える。
遠征の日数は「**その土地の雀荘をまわるのにかかる日数**」。遠いほど一度に
長く滞在するのが合理的だから長くなる、という理屈にする。
数字を触るときはこの前提で。

### 4.4 雀ドルの県はまだ振らない

いまの73人は `region`（地方）しか持たない。**県への割り当ては200人に増員するとき
まとめて行う**（HANDOVER §7 の方針に沿い、人口比ではなく下限を置いて振る）。
それまで、県で遠征しても発見の抽選は**その県の地方の未発見者**から引く
（`findCandidates` に `Geo.prefOf(pref).region` を渡す。`PREFS` は配列なので添字では引けない）。
雀ドルが `pref` を持つようになったら、県で絞る分岐を足す。

## 5. 新規開始 — 事務所名と本拠地

`title.js` の `renderSetup()` に二つ足す。

- **事務所名** — 自由入力、12文字まで。既定は「`{名前の先頭語}事務所`」
  （`playerName` を空白で切った先頭。切れなければ名前全体）。
  **入力された文字がそのまま入るので、出すときは必ず `esc()` を通す**
- **本拠地の県** — 47から一つ。地方ごとに区切って並べる。
  各県に一行の紹介文を付ける（§5.1）

保存: `officeName` / `officePref`（`playerName` と同じく最上位）。

**既存セーブに `officePref` が無い場合**、事務所画面を初めて開いたときに
一度だけ選ばせる（既定を勝手に決めない。本拠地は一度きりの選択なので）。
`officeName` が無ければ上の既定で埋める。

### 5.1 県の紹介文の書き方

規模の小さい県を「弱い」と書かない。

- 「候補が少ない」ではなく「**まだ誰にも見つかっていない**」
- 「客が少ない」ではなく「**常連が付く**」
- 規模の大きい県は「候補が多い」と同時に「**他の事務所も目を付けている**」

副題「その雀荘に、まだ見ぬ雀ドルがいる」の世界観では、地方こそ中心にいる。

## 6. 事務所画面（ハブ）

### 6.1 一日の形

```
朝（事務所）  届いた依頼を見る → 配置を確認・変更 → 「今日を始める」
昼（活動）    店：雀荘の再生（代表がいれば従来どおり。いなければ代理）
              遠征中なら：その日の遠征の出来事（発見／対局）
夜（事務所）  日報：店の収支・遠征の結果・依頼の結果・セリフ → 「明日へ」
```

「今日を始める」が `Jansou` の営業開始を呼ぶ。**雀荘画面からの営業開始ボタンは
外す**（入口を一本にする）。雀荘画面は再生と結果を見る場所になる。

**訂正（実装を読んだ結果）。** `parlor.day` を進めるのは
**既存の `settle()` の中で、昼が終わった時点**（`jansou.js` の
`day: parlor.day + 1`）。`settle` は純関数で、そこを動かすと
「スキップしても再生しても完全一致」（`jansou/spec.md` §16）が壊れる。
だから **「明日へ」は日を進めない。夜を畳んで朝へ戻すだけ**の釦にする。
朝の依頼発火（§8）は、戻った先の朝を組むときに行う。

**店がまだ無いときも、日は進む**（§1.2 の追補）。
昼を雀荘へ委譲せず、事務所の中で `Jansou.runClosedDay()` が
卓0の同じ締めを通し、そのまま夜へ抜ける。

### 6.2 朝の画面に置くもの

- **所属一覧** — 顔、名前、`pop`、`favor`、（第五段から）疲労・調子。
  **`pop` と `favor` はいまどこにも表示されていない**（HANDOVER §3）。ここが初出
- **今日の配置** — 各人が店・遠征・休み・依頼のどれか（§6.3）
- **届いている依頼** — 受ける／見送る（§8）
- **各画面への入口** — 雀荘、名鑑、チーム、（第四段まで）大会
- **雀エイト表**（第五段）

### 6.3 配置（`assign`）

全活動を同じ形に載せる。

| 配置 | 代表 | 人数 | 日数 | 消費 | 得るもの |
|---|---|---|---|---|---|
| `parlor` 店 | どちらでも | 出勤者 | 継続 | 疲労 | 場代・成長・`pop` |
| `trip` 遠征 | 必須 | 同行1〜3 | far で決定 | 費用・疲労 | 発見・契約 |
| `job:<id>` 依頼 | 不要 | 依頼が指定 | 依頼が指定 | 疲労 | 依頼が指定 |
| `rest` 休み | — | — | 任意 | — | 疲労回復 |

**配置は変更するまで継続する。** 毎朝聞かない。プレイヤーが触るのは
遠征に出るとき、依頼を受けるとき、誰かが限界に近いとき。

**雀荘のシフト（昼・夕・夜の出勤）は、この配置の `parlor` の内訳。**
シフト表のUI（`.jnRow`）を事務所に移すが、**保存の形は変えない**。
`jansou.js` が読んでいるキーをそのまま読み書きする。UIの移設であって
データの移設ではないので、`normalize()` に触れない。

**実装した形（第二段）。** 書くのは **`Jansou.setShift(store, id, slot)`
一つだけ**にした。事務所と雀荘の単体ページが同じ関数を通るので、
既定値（持っていない子は「夜だけ」）の解釈が二か所に割れない。
読むのは `Jansou.shiftOf(parlor, id)`。どちらも `parlor.shifts` を
そのまま扱うので、`normalize()` にも `assign` にも触れない。

**配置の既定は `parlor`。知らない値も `parlor` に落とす**（`Office.assignFor`）。
あとから配置の種類が増えても、古いコードが読んだときに誰かが
永久に出勤しなくなったりしないため。`trip` は `st.trip` が無ければ、
`job:<id>` は受けた依頼でなければ `parlor` に戻す（§7.5・§13）。

遠征中・依頼中の子は自動的にシフトから外れる（出勤可能者からの除外）。
出勤者が減れば `computeDay()` の入力が減るぶんだけ客足が落ちる。**これは既存の
式の範囲内**で、新しい項は足さない。

**絞るのは `prepareDay` の入口の一箇所だけ**（`Office.parlorRoster`）。
`jansou.js` は `Office` を「あれば使う」形で呼ぶので、
単体ページ（office.js を読まない経路）では「全員が店に立つ」＝
いままでどおりに落ちる。

#### 日当は契約基準（2026年9月3日に揃えた）

**出勤の有無に関係なく、所属の全員に毎日払う。**
§7.2 が「日当は既に毎日払われているので、遠征中の人件費は何も足さずに
自動でかかる。これが日数の本当のコスト」と書いており、それには
契約基準でないと辻褄が合わない。店が無い日（§1.2）も全員ぶん払っている。

**HANDOVER §4 の三局面は動いていない。**どれも全員が出勤しているので、
どちらの基準でも日当の額が同じ（`tools/measure-jansou.js` を種を固定して
前後で回し、出力が一文字も変わらないことを確かめた）。

変わるのは**誰かを `rest` にしたとき**だけで、以前は日当が浮いていたのが
いまは払い続ける。**休みは「疲労を抜くために金を払う」選択になった**。

## 7. 遠征（第三段）

### 7.1 出発時に決めること

- **行き先の県**（`Geo.PREFS`）
- **目的** — 「探す」か「口説く（相手を指名）」
- **同行者** — 所属から0〜3人。**遠征中はシフトから外れる**

出発は朝の事務所から。出た日から `days` 日、代表は不在。

### 7.2 日数と費用（初期値。第三段の終わりに再測して動かす）

```
days = 2 + far                       // 2〜7日
cost = SCOUT_COST × (1 + far) × (1 + 同行者数)
```

京都から大阪へ一人なら 3万円・2日で、いまの「一回3万」と桁が揃う。
那覇へ三人なら 72万円・7日。

**日当は既に毎日払われている**（`wageOf`）ので、遠征中の人件費は
何も足さずに自動でかかる。これが日数の本当のコスト。

### 7.3 遠征中の毎日

- **探す**: 一日一回 `drawOne`（既存）。滞在日数ぶん引ける。
  遠いほど滞在が長く、引ける回数が多い。これが「遠くの利点」の一つ
- **口説く**: 到着した日に現地で対局。相手＋代表（または同行者から一人）＋
  残りは同行者かCPU。東風戦。**代表側の誰かが相手より上の着順で終われば勝ち**。
  勝ったら `Scout.evaluate()` を回し、満たしていれば契約。
  満たしていなければ `favor` を +N して帰る。負けても同じく `favor` +少し
  （会いには行った）。**永久失敗は作らない**。次に来ればまた挑める

対局は `index.html` 側の実対局（`store.playRealMatch`）。
`scout.html` 単体ページは対局を持たないので `simulateTable` に落ちる
（`jansou.html` と同じ扱い）。

### 7.4 留守番 — 代表不在の店

遠征中の店は毎日営業する。変わるのは二点だけ。

- **代表戦（ボトル勝負・果たし状・荒らし）を `deputyOf(st)` の子が打つ。**
  `playOrSimulate` を `simulateTable` に固定し、代表の席にその子の
  `comp` / `skill` を入れる。プレイヤーは受けるかどうかも選ばない
  （出発時に「留守を任せる子」を決めておく。既定は出勤者で `comp` 最大）
- **`joinNight` が効かない**（代表がいない）

任された子は出番が付き（離脱の「出番不足」を消す）、`favor` が少し上がる。
**同じ子に任せ続けると疲労が溜まる**（第五段で数値化）。

### 7.5 帰還

帰った日の夜の日報に、留守中の日数ぶんの店の結果をまとめて出す
（**日ごとの再生はしない**。`computeDay` の結果を日ごとに積んで、
月報と同じ書式で要約）。遠征の結果（発見・契約・対局）もここ。

**遠征中はセーブに `trip` を持ち、リロードされたら続きから**。
`trip` が無い状態で `assign` に `trip` の子が残っていたら `parlor` に戻す。

## 8. 届く依頼（第四段）

### 8.1 テーブル（`src/offers.js`）

```js
{
  id: 'rookie-invite',
  kind: 'tournament' | 'contract' | 'idol',
  when: (st, roster) => boolean,   // 発火条件。日付は見ない
  once: true | false,              // 一度きりか（once なら st.offerFired を見る）
  prio: 1..9,                      // 同日に複数届いたときの並び
  days: 1,                         // 拘束日数
  members: { min, max },           // 何人送るか
  text: '...',                     // 事務所に届く文面（esc 不要のリテラル）
  payload: {...}                   // kind ごと（大会id、雀ドルid、案件の効果）
}
```

`Offers.fire(st, roster)` は朝に一度呼ばれ、`when` が真で未発火
（`once` なら `offerFired` に無い）のものを返す。`st.offers` に積む。
受けたら `assign` に `job:<id>` を入れ、`days` 経ったら結果を夜に出す。
見送ったら消える（`once` でないものはまた条件を満たせば来る）。

**発火条件を日付にしない**のは §1.3 のため。「所属が5人を超えた」
「この県を初めて訪れた」「誰かの `favor` が80を超えた」のように、
プレイヤーの状態だけで決める。

### 8.2 まず載せる三種

**大会** — 既存の5大会を、事務所の格（`playerRank` と `agency`）で届く招待にする。
`taikai.js` の大会選択画面は外し、依頼から入る。
大会は `days` を消費し、出場者は `members` で送る（既存のチーム編成を流用）。

**契約イベント** — `contract === 'event'` の6人。条件は依頼テーブルに書く
（HANDOVER §3 の推奨: `favor` ＋ `agency` ＋ 大会実績の三段）。
受けると「口説く」の遠征になる（§7.3）。`RULES.event` は
「この依頼を受けたか（`offerAccepted` に id があるか）」を見るだけに書き換える。
**天城リオ No.001 はこれで解放される。**

**アイドル活動** — `pop` の供給源。代表不要、1〜3人、`chara` で向き不向き。
結果は `pop` 上昇・報酬・`favor`・疲労。**演出は作らない。日報一行とセリフだけ。**
成果は雀荘の「推しファン」として床に現れる（見た目は既に第三段で入っている。
売上への反映は §11 の再測とセット）。
案件の一部は対局付き（テレビ対局・ファン対局会）で、送った子が打つ。
`simulateTable` で確定、勝てば `pop` が跳ねる。

### 8.3 依頼の発生数

その日届く依頼の数は本拠地の `scale` で重みづける（都市は多い）。
ただし **`once` の契約イベントは規模に依らず条件だけで届く**。

## 9. 疲労と調子（第五段）

役割が逆なので、はっきり分ける。

- **疲労 `fatigue`** 0〜100 — プレイヤーが**管理する**もの。行動で溜まり、休みで抜ける。
  高いほど `comp` の補間位置を一時的に戻す（実力が落ちるのではなく判断が鈍る）。
  **新しい計算系は作らない**。既存の補間に一時的な係数を掛けるだけ
- **調子 `cond`** −2〜+2 — プレイヤーが**受け入れる**もの。毎朝決まる。
  疲労が高いほど悪い目が出やすい。その日の対局の `skill` に薄く効く

乱数は朝に引いて確定させる（`computeDay` の前）。**再生層では引かない**。

数値はここでは決めない。第五段で三局面（HANDOVER §4）＋遠征＋依頼を
まとめて再測してから置く。回復しきる方向に寄せる（§1.3）。

### 9.1 雀エイト表

全国上位八人。**強さ（大会実績・`comp`）と人気（`pop`）の二軸**。
未契約の子も載る。自分の子を割り込ませていくのがゴール。
表は事務所の壁（朝の画面）に出す。**ライバル事務所の名前はここで初めて出る**
（引き抜きの主体として既に存在していることになっている）。

## 10. セーブ

**最上位に足す**（`parlor` の下ではない。`Jansou.normalize()` に触れないため）:

```js
officeName: '',            // 事務所名
officePref: null,          // 本拠地の県 key。null なら初回に選ばせる（§5）
assign: {},                // { [charaId]: 'parlor'|'trip'|'rest'|'job:<id>' }
trip: null,                // 遠征中なら { pref, purpose, target, members, deputy,
                           //             dayLeft, log: [] }
offers: [],                // 届いている依頼（受ける前）
offerFired: [],            // once の依頼で既に発火した id
offerAccepted: [],         // 受けた依頼の id（RULES.event が見る）
fatigue: {},               // { [charaId]: 0..100 }  第五段
cond: {},                  // { [charaId]: -2..2 }   第五段
```

`comp` と同じく最上位の `{ [id]: value }` の形に揃える。

**読むときは必ず既定値で埋める。** 既存セーブに一つも無くても動くこと。
**書くときは知らないキーを残す**（`Object.assign({}, s, {...})`）。
`parlor.day` は既存のまま、`Jansou` が所有する。

## 11. 再測が要るもの

以下は HANDOVER §4 の「調整済みの数値」を動かす。**第三段の終わりと第五段で、
まとめて測る。** 途中の段で個別に触らない。

- **開店前の日当。**店が無い期間も日当が出ていくようになった（§1.2）。
  開店資金50万に何日かかるか、序盤の収支がどう変わるか。
  **第一段で入ったが、数字は触っていない。**ここで測る。
  **所持金の下限は付けない。**マイナスは「給料の遅配」として許し、
  定員のソフト化（`ROADMAP.md` [C]）で離脱の警告に繋げる
- スカウト一回の費用「3万」→「3万 × 遠さ × 人数 ＋ 日数」に変わる。
  「雀荘一日の利益と釣り合う」という基準が、遠征一回では「日数ぶんの店の利益」に対して
  釣り合うかに変わる
- 遠征中は出勤者が減り、`joinNight` が効かず、代表戦が代理になる。序盤の
  一日の利益 +3.3万がどれだけ落ちるか
- 大会が日を消費する。「120大会まわして所属8人・B級」が何日相当になるか
- 推しファンの売上反映（`docs/design/jansou/spec.md` §6.1 で先送りしたもの）。
  アイドル活動が `pop` を上げる以上、ここは繋がないと片手落ちになる。
  **`computeDay()` の入力に favor 由来の項を足す**のはこの再測のときだけ

- **出勤人数が席数に足りなければ客足が落ちる**（A5 で入れる。2026年9月3日に決めた）。
  いまは `computeDay()` が `Math.min(capacity, demand)` で頭打ちにしていて、
  **終盤は出勤者の `pop` が余っている。**卓8・12人の局面で測ると、
  同行3人を遠征に連れ出しても客数が 221人 から1人も動かない
  （`tools/measure-office.js`）。つまり **終盤の遠征はノーコスト**。

  これは遠征以前の問題で、**「終盤は誰を出勤させても同じ」**という
  既存の穴がそのまま出ているだけ。だから遠征側では直さない。

  **`capacity` は触らない。**あそこは席数と回転の上限で、
  内装・卓の型・卓数の意味がすべて乗っている。動かすと三局面が全部ずれる。
  代わりに **`slotWorkers`（出勤人数）が席数に対して足りないときに
  需要を削る項**を足す。人が足りなければ卓を開けられない、という理屈。

  **A5 でやるのは、推しファンの売上反映と同じ再測に相乗りさせるため。**
  どちらも `computeDay()` の入力を増やす変更で、三局面を測り直すことになる。
  二度測るより一度で済ませる（§11 の冒頭「途中の段で個別に触らない」）。

測り方は二つ。どちらも種を固定できるので、前後の比較が完全一致で見られる。

```
node tools/measure-jansou.js    直営店の三局面（客／一日の利益）
node tools/measure-office.js    遠征と日進行の釣り合い（A3 の四項目）
```

依頼の日を混ぜたぶんは `measure-office.js` に足していく。

- **本拠地の移転・支店** — 器だけ空けておく（`officePref` を書き換えれば動く形）。今回は選ばせない

- **疲労・調子の数値** — 第五段の再測で置く。それまでフィールドは0

## 13. テストと検証

**`node tools/test-office.js`**（純関数）:

- `Geo.distKm` が対称。京都→大阪が far 0、京都→那覇が far 5
- 47県すべての `region` が `REGIONS` のいずれかに一致する

- （第五段）朝の `cond` を rng 固定で引き、同じ種なら同じ値

**ブラウザ検証**（`http://localhost:8765`、Puppeteer `--no-sandbox`）:

- 新規開始 → 事務所名と県を選ぶ → 事務所に着く → 「今日を始める」→ 雀荘の再生 → 夜の日報 → 「明日へ」→ 朝

- 遠征中にリロード → 続きから
- 縦持ち幅（〜380px）で事務所の朝画面が収まる（表紙と同じく `#scroll` の中で流す）
- 文字がすべて丸ゴシックで豆腐が出ない（**47県名を全部出して確認**）

## 14. 進め方

一度に全部作らない。各段階で動く状態にしてコミットし、止まる。
**着手前にこの指示書を読んで、食い違い・不明点を先に報告すること。**

1. **【完了】ハブと日の一本化** — `office.js` の朝と夜。既存五画面を配下に付け替え。
   営業開始を事務所からのみに。`title.js` に事務所名と県。`geo.js` のデータ。
   **まだ何も日を消費しない**（大会・スカウトは従来どおり回数制のまま）
2. **【完了】配置とシフトの移設** — `assign`。雀荘のシフト表UIを事務所へ（データは動かさない）。
   `fatigue` / `cond` のフィールドだけ足す（値は0、表示もまだ）
3. **【完了】遠征** — `planTrip`、出発と帰還、留守番、現地の対局。`scout.js` の「探す」を置き換え。
   **一度目の再測は済んでいる**（`node tools/measure-office.js`）が、
   **数字はまだ動かしていない**。ここまでで公開判断ができる
