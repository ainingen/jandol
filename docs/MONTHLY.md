## 2. 月とは何か

### 30日をひと月にする

**`MONTH_DAYS = 30`。** 恣意的な数字ではない。

`wageOf()` はすでに `BASE_WAGE + salary / 30` と書いてある。
**日当は最初から「月給の三十分割」だった。**
30日をひと月にすれば、30日ぶんの日当の合計がちょうど月給一人分に一致する。
月報の「人件費」が年俸表と突き合わせられる数字になる。

```js
const MONTH_DAYS = 30;   // wageOf() の salary/30 と対。片方だけ動かさないこと
```

`wageOf` の `/30` もこの定数を見るように書き換える（**値は変えない**ので
`docs/HANDOVER.md §4「直営店の経済」`の実測値は動かない）。

### 時計は `parlor.day` ひとつだけ

`parlor.day` は営業のたびに +1 される通し日数。**これを唯一の時計にする。**

- **`parlor.day` はリセットしない。** `parlor.log` も `parlor.total` もこれを基準に
  積んである。月初で0に戻すと過去の記録が読めなくなる
- 「第何期か」「その月の何日目か」は `parlor.day` と `parlor.month.from` から**導出する**。
  別に持たない（二つ持つと必ずずれる）

```js
const inMonth = parlor.day - parlor.month.from;      // 0 始まり
const isMonthEnd = inMonth + 1 >= MONTH_DAYS;        // その日の営業を終えた時点で判定
```

`day % 30 === 0` にしない理由は §6（既存セーブの移行）。
`from` を持てば、途中から始めたプレイヤーも**まるまる30日ぶんの月報**を受け取れる。

### 時計は雀荘の中に置く（ゲーム全体の暦にはしない）

大会は日数を進めない。だから「月」はいまのところ**店の営業日**でしかない。
`state.day` に昇格させず `parlor.day` のままにする。

将来ゲーム全体の暦にしたくなったら、`parlor.day` を `state.day` に引き上げ、
大会や スカウトも日を消費する形にする。そのときも
`parlor.month.from` の作りはそのまま使える（`from` が全体の暦を指すだけ）。

## 3. 月末に何を見せるか

**七つの節。上から読み下せば「今月どうだったか」が分かる順に置く。**
数字は書式の例であって、実測前の仮の値。

### (1) 見出し

```
      第 3 期  決算
    61日目 〜 90日目
```

### (2) 売上の帯 — 時間帯ごと

```
昼  12〜17時    1,240人     1,984,000円  ████░░░░░░
夕  17〜21時    1,690人     3,549,000円  ███████░░░
夜  21〜26時    2,310人     6,006,000円  ██████████
───────────────────────────────────────
売上                       11,539,000円
```

**この三本の合計が売上に厳密一致する（§7 / 旧 §5.3）。**
帯の長さはCSSの `width:%` で描く。canvasは使わない。

どの時間帯が稼ぎ頭かが月単位で見えると、シフトの組み方が変わる。
いまは一日ぶんのぶれが大きすぎて判断材料にならない。

### (3) 収支の帯

```
売上                       +11,539,000円
臨時収入（祝儀・荒らし・お忍び）  +  420,000円
日当（延べ 180人）           −  1,260,000円
家賃・光熱（30日）           −    600,000円
───────────────────────────────────────
今期の収支                 +10,099,000円     先期比 +18%
```

**四本の合計が収支に厳密一致する。** 各項は日ごとの確定値を整数で足しただけなので、
`Σ（その日の profit）` とも一円まで一致する（§7 に検算を書く）。

### (4) 客

```
のべ客数     5,240人      一日平均  175人
満卓だった日  18日 / 30日
常連          312人  （先期 268人 → +44）
```

**満卓の日数**は、いまの日報では「満卓」の印が出て消えるだけで残らない。
卓の増設をいつ決めるかの根拠になる。

### (5) 雀ドルの人気

```
今月いちばん客を呼んだ子

  ① 桐生ひかり    人気 92 × 出勤 28日 = 2,576
  ② 白鳥さくら    人気 78 × 出勤 30日 = 2,340
  ③ 神楽坂まゆ    人気 85 × 出勤 22日 = 1,870

伸びた子   桐生ひかり +3.2 ／ 白鳥さくら +2.8（C級に昇格）
```

**「人気 × 出勤日数」は月報を出すための表示上の指標**であって、
`computeDay()` に入れる値ではない（§7）。
`computeDay` は `slotPop`（その時間帯の出勤popの合計）しか見ておらず、
そこは一切触らない。

これは四本柱の「人気」を初めて数字として返す場所になる。
いまは pop が高い子を雇っても、客が増えたのかどうかがプレイヤーに見えていない。

### (6) できごと

```
ゲスト来店      6回（うちもてなし 4回）
雀荘荒らし      3回   2勝1敗   +100,000円
雑誌の取材      2回
卓の故障        1回
```

### (7) 評判

```
評判  38 ──────────▶ 52     +14
      期首              期末
```

### 前期との比較

`months[]` の直前の要素があれば、売上・収支・客数・常連に差分を添える。
初回（比較対象が無い）は差分を出さない。**「−」や「±0」を出さない**
（前期が無いことと変化が無いことは違う）。

## 4. 締めをどの画面でどう出すか

### 結論：営業の再生と地続き。ただし読み返せる入口を別に置く

**月末の営業を終えた直後、日報のあとにもう一枚出す。** 新しいタブは作らない。

```
「今日の営業をはじめる」
   ↓
（イベント・実対局）
   ↓
30日目の日報   [ 閉店する ]
   ↓
第3期 決算     [ 来月へ ]      ← ここが新しい
   ↓
雀荘の画面に戻る
```

### 地続きにする理由

- **月報は「場所」ではなく「瞬間」だから。** タブにすると営業と切り離され、
  見に行かれないまま古くなる。締めは営業の結末として出会うのが正しい
- 日報がすでに `ask()` の一枚（`html:` を渡して `jnRepWrap` で組む形）でできている。
  **月報はその大きい版で、仕組みを一つも増やさずに済む**
- 「一回押す＝一日進む」という営業のリズムを壊さない。
  画面遷移を挟むとリズムが切れる
- 新しい画面・新しいナビゲーション状態・新しいセーブ項目（現在地）が要らない

### 読み返す入口

締めは一度きりで流れてしまうので、雀荘の画面に

```
      ［ 先月の決算を見る ］
```

を置く。押すと**保存しておいた月報（`parlor.months` の末尾）を
同じ `ask()` で開き直す**。

**開き直しても数字は一切作り直さない。**締めた時点の確定値を並べるだけ
（§7 / 旧 §1）。だから何度開いても同じものが出る。

### 演出

- 帯は左から伸びる（CSSの `transition: width`）。節は上から順に薄く現れる
- **全部で1.2秒くらい。どこかを触ったら即座に最終形へ飛ぶ**
  （『おまかせ』と同じ考え方。待たせない）
- **数字は最初のフレームの前にすべて確定している。**アニメーションは
  確定済みの値へ向かって動くだけで、途中の値を計算しない（§7 / 旧 §1）

### canvas は使わない

**表紙の `#cover` 一枚だけという決めごとを守る**（README「表紙とサムネイル」）。
帯もグラフも `div` の幅で描く。
`jansou.css` に `.jnRepTrack` / `.jnRepFill`（評判のバー）がすでにあるので、
同じ作りを使い回す。

## 5. 常連（新しい概念）

「常連の数」は今のコードに無い。**新しく作る。**

### 何であるか

**常連は在庫のような「たまるもの」**。月末に客数と評判から増え、少しずつ減る。
一日ではほとんど動かず、月単位で効いてくる数字にする。
売上や利益と違って**貯まっていく実感**を返すのが役目。

```js
/* 純関数。closeMonth から一度だけ呼ぶ */
function computeRegulars(prev, month, rep) {
  const keep = 0.85;                                  // 一月に15%が離れる
  const gain = month.guests * 0.02 * (0.5 + rep / 200);
  return Math.round(prev * keep + gain);
}
```

- 減衰があるので青天井にならない
- 評判が高いほど、同じ客数でも常連になりやすい
- 客が来ない月が続けば減る

**この係数は仮。** 引き継ぎ書 §9「数値は測ってから決める」に従い、
実装時に `computeDay` を数百月ぶん回して分布を見てから決める。
序盤／中盤／終盤（§4 の三局面）でそれぞれ何人に落ち着くかを表にして残す。

### 常連は経済に効かせるか — 決めてほしい（§10）

**案A（推奨・初回はこれ）… 表示だけ。**
月報に出るだけで、売上には影響しない。
**経済のバランスに一切の影響が無い**ので、引き継ぎ書 §4 の実測値
（序盤+3.3万／中盤+10.6万／終盤+26.1万）をそのまま維持できる。
「積み上がっている」という手応えだけを先に返す。

**案B … `pullBonus` に小さく乗せる。**

```js
pullBonus += Math.min(0.10, regulars / 3000);   // 上限 +10%
```

`pullBonus` は `computeDay` が**すでに受け取っている引数**（取材バフが使っている）。
だから `computeDay` の中身は一行も変わらない — 前提は守れる。
ただし**客足は確実に増えるので、§4 の三局面を測り直す必要がある。**
上限を10%に切っているのは、取材バフ（+15%・三日）より弱くして
「効くが支配しない」に留めるため。

案Aで入れておけば、あとから案Bに移すのは一行足すだけ。
逆（効かせてから外す）はプレイヤーの体感が下がるので難しい。
**まず案Aを推す。**

## 6. 月をまたぐ処理

### 大原則：月末は「締め」であって「リセット」ではない

**リセットするのは集計の入れ物（`parlor.month`）ひとつだけ。
店にあるものは全部そのまま翌月へ持ち越す。**

| 何を | 月をまたぐと | なぜ |
| --- | --- | --- |
| `parlor.day` | **持ち越す**（増え続ける） | 通し日数。`log` と `total` の基準 |
| `parlor.rep` 評判 | **持ち越す** | 店の評判は月で消えない |
| `parlor.buffs` | **持ち越す**（日数の減りかたも変えない） | 下に詳述 |
| `parlor.shifts` | **持ち越す** | 毎月組み直させるのは手間なだけ |
| `parlor.tables` `interior` `auto` `sign` | **持ち越す** | 買った設備 |
| `parlor.log` 直近7日 | **持ち越す** | 月と無関係の直近履歴 |
| `parlor.total` 通算 | **持ち越す** | 生涯累計 |
| `parlor.regulars` 常連 | **持ち越す**（減衰は月末に一度） | §5 |
| `state.money` `comp` `compMax` `grades` `favor` | **持ち越す** | 店の外の値。触らない |
| `parlor.month` 集計の入れ物 | **空にする** | ここだけ |

### buffs は月をまたいでもそのまま減る

「雑誌の取材が入った（三日間 客足が伸びる）」が28日目に出たら、
**31日目・32日目にも効く。**月末で切らない。

- バフは**店に起きた出来事**であって、会計期間とは関係が無い
- 月末で切ると「取材は月末に来ると損」という妙な読みが生まれる
- 「卓の故障（明日は一卓閉める）」も同じ。月末に壊して逃げられないようにする

実装は**いま動いているコードのまま**（`days - 1` して `days > 0` で残す）。
月末処理はここに一切触らない。**触らないことが設計判断。**

### 在庫について

**在庫（飲み物・軽食などの仕入れ）はいまのコードに存在しない。
今回も入れない。** 月報に出すものが増えるだけで、決算そのものは成立する。

ただし**あとから足したときに月末処理を書き直さずに済むよう、扱いだけ決めておく。**

- **在庫は物であって金ではない。** 棚に載っているものは月末に消えない。
  **buffs と同じで、そのまま翌月へ持ち越す**
- **月報に出るのは金の動きだけ** — 「仕入れ ▲◯◯円」「廃棄 ▲◯◯円」を
  **収支の帯に一本足す**。在庫の残数は帯ではなく、客の節に併記する
- **在庫数そのものを売上の帯に混ぜない。**混ぜると §7 の
  「帯の合計＝売上」が崩れる。**これが在庫を足すときのいちばんの罠**

つまり在庫は「収支の帯が一本増えるだけ」で収まる。
今回の `accrue()` に `stockCost` の器だけ空で用意しておけば、
月末処理は将来も無改造で通る。

### 月給を月末にまとめて払うのは「やらない」

月の概念ができると「日当をやめて月末に月給を一括で払う」が自然に見える。
**これはやらない。**

- 合計額は同じ（`salary/30 × 30`）だが、**現金の流れかたが変わる。**
  月末に大きな支出が来る形にすると、月初に設備を買ってしまったプレイヤーが
  月末に破綻する。序盤の +3.3万/日 という設計（§4）が崩れる
- 引き継ぎ書 §4 の実測値は**すべて一日単位**で取ってある。測り直しになる

**日当は毎日払ったまま。月報はその合計を「人件費」として見せるだけ。**

## 7. 守る前提と、その検算

依頼で挙がった四つの前提を、どう守るかと**どう確かめるか**。

### 先に全部計算・再生は演出のみ（旧 §1）

**締めの計算は `closeMonth()` という純関数に一度だけ集める。**
返ってくる `report` オブジェクトを、描画側はただ読む。

```js
/* 純関数。乱数を引かない。DOMを触らない */
function closeMonth(month, prevReport, parlor, roster) { /* → report */ }

/* 描画。report を読むだけ。計算は書式（カンマ区切り・%）まで */
function renderMonth(report) { /* → HTML文字列 */ }
```

**守り方：`renderMonth` の中に四則演算を書かない。**
帯の長さの `%` すら `closeMonth` が `report` に入れて渡す。
そうすれば「読み返し」でも「アニメーション」でも同じ数字が出ることが保証される。

**確かめかた：** node から `closeMonth()` を呼び、返った `report` を
そのまま二回 `renderMonth` に通して**文字列が一致する**ことを見る。

### 帯の合計が売上に厳密一致（旧 §5.3）

**`month.sales` を独立した変数として持たない。帯の合計として定義する。**
`computeDay()` が `sales: slots.reduce(...)` と書いているのと同じ形。

```js
月の売上   = Σ month.slots[k].sales           （k = 昼・夕・夜）
月の収支   = 月の売上 + extra − wages − util
```

積み上げる値は**すべて整数**なので誤差が出ない
（場代は `guests * fee`、日当は `wageOf` が `Math.round`、
家賃は `8000 + tables*1500`、臨時収入も整数）。

**確かめかた：** 30日ぶん `accrue()` して

```
Σ month.slots[k].sales      === month.sales           （一円まで）
sales + extra − wages − util === Σ（その日の profit）  （一円まで）
```

を assert する。**月報の帯は per-day の値を足したものだけを出し、
平均や割合から逆算した数字を帯に混ぜない。**

### `computeDay` の数値には触らない

**`computeDay()` の本体は一行も変えない。**

- 積み上げは `computeDay` が**返した後**、`runDay()` の締めのところで行う

## 9. 先に書いておく罠

### `normalize()` は知らない項目を捨てる（重大）

`README`は「各画面はセーブを読むとき、自分が知らない項目もそのまま残すこと」と
書いているが、**`Jansou.normalize()` は既知のキーだけでオブジェクトを組み直している。**

```js
function normalize(p) {
  p = p || {};
  return { open: ..., day: ..., /* 列挙されたキーだけ */ };
}
```

つまり **`normalize()` に足し忘れた `parlor` のキーは、次のセーブで消える。**
`month` を足しても `normalize()` に書かなければ、
**一日営業するたびに集計が消えて、月報が永遠に0になる。**

症状は「月報は出るが全部0」。気づきにくい。**最初に `normalize()` を直すこと。**

### `parlor.log` から月を集計しない（重大）

`log` は `.slice(-7)` で**直近7日しか残らない**。
30日ぶんを合計しようとしても7日ぶんしか無い。

**月の集計は `parlor.month` に独立して積むこと。** `log` は表示用の別物。

### `months[]` は放っておくと無限に伸びる

セーブは localStorage。1年遊べば12件、3年で36件。
月報一件が仮に2KBとして、青天井にすると効いてくる。

**`.slice(-12)` で直近12期だけ残す。**
生涯累計は `parlor.total` が別に持っているので情報は失われない。

### 帯に平均や割合から作った数字を混ぜない

「一日平均175人」は帯ではなく客の節に置く。
帯に平均を混ぜると合計が売上に一致しなくなる（§7）。
**帯に出していいのは per-day の値を足したものだけ。**

### 月末の判定を `day % 30` でやらない

既存セーブは `day` が中途半端な値（47日目など）で止まっている。
`% 30` にすると、そのプレイヤーの初回の月報は
**13日ぶんしか入っていないのに「一ヶ月」として出る。**

`month.from` からの経過で判定する（§2 / §6）。

### 月報の `ask()` の中で実対局を呼ばない

日報のあとに月報を出すが、**月報の側からイベントや対局を起こさない。**
`ask()` は Promise を返すだけの単純なもので、入れ子にすると
おまかせ（§4 引き継ぎ書）の宙に浮いた Promise と同じ罠を踏む。
**月報は表示だけ。何も起こさない。**

### 見た目は縦横の両方で確かめる

月報は日報より縦に長い。`.popupBox` からはみ出す。
`python3 -m http.server` 越しに開き、**縦持ちと横持ちの両方**を描画する
（引き継ぎ書 §4「見た目を変えたら、必ず縦横の両方を描画して確かめること」）。

**いちばん長くなる状態で測る** — 出勤12人・イベント全部・昇格あり・前期比あり。
